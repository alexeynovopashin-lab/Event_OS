# Сервер ядра в Yandex Cloud: что сделать руками (срез 1, только Россия)

Код готов и проверен на компьютере, но **в облаке пока ничего не создано**. Здесь — всё, что делаете вы
в консоли Yandex Cloud. Занимает около получаса. Соль и пропуски никому не показывайте и в чат не вставляйте.

Что получится: одна функция (`eventoscore`) и одна база (`eventos-core`). Машины, которую надо обновлять, нет.
Это шаги 6–10 из инструкции `core_server_howto_2026-11-23.md`; шаг 7 (закрытое хранилище `eventos-avatars`)
**не нужен**: в срезе 1 аватарки лежат прямо в базе (одна аватарка — около 50 КБ). Если фотографов станет много,
их можно будет переложить в хранилище, приложение этого не заметит.

## Шаг А. На Mac, один раз (готовим архив и соль)

В Терминале, в папке с Event OS (после слияния pull request — на ветке `main`):

```bash
cd server
npm test                  # должно быть: pass 33, fail 0
cd yandex
./build.sh                # создаст dist/eventoscore.zip (около 3 МБ) — его загрузим в функцию
openssl rand -hex 32      # длинная случайная строка — это «соль». Скопируйте её, никому не показывайте
```

Соль хранится только в настройках функции в облаке. Потеряете её — все выданные пропуска перестанут действовать
(приложения зарегистрируются заново, аватарки загрузятся из очереди сами). Поменять соль потом нельзя без этого эффекта.

## Шаг Б. В консоли Yandex Cloud, каталог `eventos`

1. **База.** Managed Service for YDB → «Создать базу данных» → тип **Serverless**, имя `eventos-core`.
   Когда база создана, откройте её и скопируйте строку **«База данных»** (выглядит как `/ru-central1/b1g…/etn…`).
   Это не секрет, но понадобится в пункте 4.
2. **Таблицы.** В базе: «Навигация» → «Новый SQL-запрос» → вставьте **весь** файл `server/yandex/schema.yql` →
   «Выполнить». Должны появиться четыре таблицы: `devices`, `avatars`, `moved`, `rate`.
3. **Сервисный аккаунт** (имя `eventos-core`): каталог → «Сервисные аккаунты» → создать, роль **`ydb.editor`**
   (на каталог `eventos`). Других ролей не нужно.
4. **Функция.** Cloud Functions → «Создать функцию» с именем `eventoscore`; в редакторе:
   - среда выполнения **Node.js 22**, способ «ZIP-архив», загрузить `server/yandex/dist/eventoscore.zip`;
   - точка входа **`index.handler`**; таймаут 20 секунд; память 256 МБ;
   - сервисный аккаунт — `eventos-core` из пункта 3;
   - переменные окружения (две): `PASS_SALT` = ваша соль из шага А, `YDB_DATABASE` = строка из пункта 1;
   - «Создать версию». Затем на странице функции включите **«Публичная функция»** (как у `lightplanweather`) и
     скопируйте **«Ссылку для вызова»** (`https://functions.yandexcloud.net/<длинный номер>`).
   Если консоль откажется принять архив из-за размера (прямая загрузка ограничена — точный предел **не проверен**),
   она сама предложит загрузить его через Object Storage: согласитесь.
5. **Запись в `ws:INDEX.md`** (Region mirrors, строка `event_os`): что создано — база, функция, сервисный аккаунт и
   ссылка. Только то, что вы видели в консоли. Это может сделать сессия по вашим словам.

## Шаг В. Проверка (одной командой)

На Mac, в папке `server/yandex`:

```bash
MODE=op ./check.sh https://functions.yandexcloud.net/<номер функции>
```

**Измерено 23.11 на первом развёртывании:** адреса вида `…/<номер>/v1/health` Яндекс до функции не пропускает и сам
отвечает `400 invalid functionID`. Работает только запасной путь «через вопросительный знак»: `…/<номер>?op=health`.
Поэтому `MODE=op` обязателен; приложению Light Plan нужна правка адресов (вопрос передан в хаб).

Скрипт сам создаёт тестовое устройство с **выдуманным** номером, проверяет все пункты шагов 0–3 и стирает за собой.
Пропуск он не печатает. Если первая проверка (связь) не прошла, скрипт останавливается: остальные строки были бы
ложными. Ошибка засчитывается зелёной, только если её вернул наш сервер (код и `{"error":"…"}` в теле), а не сам Яндекс.

| Что видите | Что значит | Что делать |
|---|---|---|
| «Итого: 27 зелёных, 0 красных» | Всё работает | Прислать итог в тред EventOS |
| `{"ok":false,"error":"not_configured","missing":[…]}` | Не заданы переменные из пункта 4 | Добавить перечисленные переменные и создать новую версию |
| `500 server_error` | Функция не смогла открыть базу | Журнал функции («Логи»): строка `init_failed` с `kind`, `code` и началом сообщения (без путей). Пришлите её |

Вручную:

```bash
curl -s "https://functions.yandexcloud.net/<номер>?op=health"
```

Ожидаемый ответ: `{"ok":true,"core":"0.1.0","home":"ru","time":"…","api":["devices","avatar"]}`.

## Если версия уже выложена и нужно обновить код

Новая версия функции из нового архива (`./build.sh`) с теми же настройками и **той же** солью. Если соль не сохранили
(её нигде нельзя прочитать обратно, кроме настроек функции), а пропусков ещё никто не получал — можно сгенерировать новую.

## Что после

Когда `check.sh` зелёный, ядро пишет адрес в `platform_hub:QUEUE/lightplan.md`; сессия Light Plan подставляет его
вместо «сервера нет», проверяет на телефоне и **в тот же день** меняет подпись конфиденциальности («не храним на
сервере ничего личного»). Дом «мир» (Cloudflare) — позже, когда вы привяжете карточку; общий код для него уже готов.

## Что хранится и что пишется в журнал

- В базе: хеш пропуска, два ключа-хеша от номера (по ним нельзя вернуть номер, не зная соли), страна, версия
  приложения, имя (только если человек сам ввёл), время регистрации, аватарка (картинка без метаданных).
  Номера и самого пропуска в базе **нет**.
- В журнале функции: маршрут, `deviceId`, код ответа, время. Телефонов, ID и пропусков нет.
  Журналы самого Яндекса (адреса запросов) личного тоже не содержат: ID и номера в адресах не ходят.
