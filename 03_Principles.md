# Purpose

Данный документ определяет фундаментальные принципы проектирования Event OS.

Это не список рекомендаций.

Это набор архитектурных законов, которым должны соответствовать:

- код;
- интерфейсы;
- UX;
- бизнес-логика;
- новые функции;
- решения команды.

Если новая идея нарушает один из принципов, необходимо пересмотреть саму идею.

---

# Principle 01 — Event First

Главной сущностью системы является **событие (Event)**.

Не пользователь.

Не компания.

Не клиент.

Не подрядчик.

Все сущности существуют только как часть события.

Если объект невозможно связать с мероприятием, он не относится к модели данных Event OS.

---

# Principle 02 — Context Over Data

Система управляет не данными.

Система управляет контекстом.

Информация становится ценной только тогда, когда помогает пользователю принять следующее решение.

Документ сам по себе не имеет ценности.

Ценность появляется тогда, когда пользователь получает этот документ именно в тот момент, когда он необходим.

---

# Principle 03 — Single Source of Truth

Любая информация существует только в одном месте.

Запрещается:

- копирование информации;
- параллельное хранение версий;
- дублирование документов;
- повторный ввод одинаковых данных.

Любое изменение производится один раз.

Все связанные объекты получают обновление автоматически.

---

# Principle 04 — Timeline Is The Workspace

Timeline — главный интерфейс системы.

Не календарь.

Не список задач.

Не dashboard.

Не таблица.

Timeline представляет собой живую временную модель события.

Каждая сцена Timeline содержит собственный контекст.

Любая работа начинается через Timeline.

---

# Principle 05 — Navigator, Not Dashboard

Главный экран сопровождает пользователя.

Он не показывает статистику.

Он не показывает все разделы системы.

Он показывает только следующий необходимый шаг.

Event OS работает по тем же принципам, что автомобильный навигатор.

---

# Principle 06 — Deliver Context, Don't Make People Search

Пользователь не должен искать информацию.

Информация должна приходить к пользователю самостоятельно.

Система обязана сообщить об изменениях до того, как пользователь начнет их искать.

Поиск является резервным механизмом.

Основной механизм — доставка контекста.

---

# Principle 07 — Relevance Over Visibility

Видимость и релевантность — разные понятия.

Права доступа определяют:

> Что пользователь может увидеть.

Контекст определяет:

> Что пользователь должен увидеть сейчас.

Даже если пользователю доступен весь проект, система показывает только наиболее релевантную информацию.

---

# Principle 08 — One Next Decision

Каждый экран отвечает только на один вопрос:

> Что делать дальше?

Если экран заставляет пользователя самостоятельно определять следующий шаг, значит интерфейс спроектирован неправильно.

---

# Principle 09 — Progressive Disclosure

Контекст раскрывается постепенно.

Пользователь получает информацию порциями.

Только тогда, когда она становится актуальной.

Система никогда не перегружает пользователя всей информацией одновременно.

---

# Principle 10 — Rescue Room

Каждый пользователь получает собственную "выручай-комнату".

После открытия проекта система автоматически отвечает:

- где я;
- что происходит;
- что изменилось;
- что делать дальше;
- что может помешать моей работе.

Пользователь никогда не начинает работу с пустого экрана.

---

# Principle 11 — Every Role Has Its Own Journey

У каждого участника существует собственный маршрут внутри одного события.

Фотограф проходит один путь.

Ведущий — другой.

Флорист — третий.

Молодожены — четвертый.

Все используют один проект.

Но никто не обязан видеть одинаковый интерфейс.

---

# Principle 12 — Human Attention Is Limited

Главный ресурс пользователя — внимание.

Любая функция должна уменьшать когнитивную нагрузку.

Если новая возможность увеличивает количество решений, которые принимает пользователь, она должна быть переработана.

---

# Principle 13 — AI Is Optional

ИИ никогда не является обязательным компонентом платформы.

Все функции должны работать без него.

Искусственный интеллект усиливает существующую систему.

Он не заменяет архитектуру.

---

# Principle 14 — Human Makes Decisions

Последнее решение всегда принимает человек.

Система может:

- предупреждать;
- анализировать;
- рекомендовать;
- прогнозировать;
- объяснять.

Она не принимает решения самостоятельно.

---

# Principle 15 — Communication Belongs To Objects

Общение не существует отдельно.

Любая коммуникация относится к конкретному объекту.

Например:

- сцена Timeline;
- документ;
- подрядчик;
- задача;
- локация;
- файл.

Пользователь не ищет информацию в общем чате.

Он открывает объект и видит всю связанную коммуникацию.

---

# Principle 16 — Everything Has History

Любое изменение сохраняется.

Система должна отвечать на вопросы:

- кто изменил;
- когда изменил;
- что изменил;
- почему изменил.

История проекта является частью контекста.

---

# Principle 17 — Temporary Participation

Не каждый участник становится постоянным пользователем платформы.

Большинство подрядчиков участвуют в проекте временно.

Система должна позволять быстро:

- пригласить;
- подключить;
- выполнить работу;
- завершить участие.

Без сложной регистрации и длительного обучения.

---

# Principle 18 — Modular Platform

Никто не обязан использовать всю платформу.

Каждый пользователь работает только с теми возможностями, которые относятся к его роли.

Функции должны подключаться модульно.

---

# Principle 19 — Desktop And Mobile Have Different Jobs

Компьютер предназначен для подготовки.

Телефон предназначен для сопровождения.

Интерфейсы не должны быть одинаковыми.

Desktop помогает строить проект.

Mobile помогает проживать проект.

---

# Principle 20 — The System Learns The Project

Пользователь не должен адаптироваться к интерфейсу.

Интерфейс должен адаптироваться к проекту.

По мере развития мероприятия меняется и представление информации.

Контекст становится динамическим.

---

# Principle 21 — Platform Before Features

Каждая новая функция должна усиливать платформу.

Если возможность существует изолированно и не интегрируется в граф событий, Timeline и контекстную модель, она не должна входить в продукт.

---

# Principle 22 — Simplicity Is A Feature

Простота является конкурентным преимуществом.

Любое усложнение интерфейса требует архитектурного обоснования.

Если функцию невозможно объяснить за несколько предложений, скорее всего она требует переработки.

---

# Principle 23 — Scale Without Rebuild

Архитектура должна одинаково работать:

- для одного фотографа;
- для небольшой команды;
- для свадебного агентства;
- для сети агентств;
- для международных проектов.

Рост пользователей не должен требовать изменения архитектуры.

---

# Principle 24 — Invisible Software

Идеальная система незаметна.

Пользователь думает не о приложении.

Он думает о мероприятии.

Интерфейс сопровождает работу, но никогда не становится ее центром.

---

# Principle 25 — Protect Human Creativity

Event OS автоматизирует организацию.

Не творчество.

Фотограф остается фотографом.

Ведущий остается ведущим.

Организатор остается организатором.

Система берет на себя управление контекстом, освобождая людей для работы, требующей опыта, вкуса и человеческого общения.

---

# Final Statement

Каждый принцип существует ради одной цели.

**Освободить человека от необходимости помнить, искать и синхронизировать информацию.**

Event OS должна сопровождать пользователя через событие так же естественно, как навигатор сопровождает водителя через маршрут.

В нужный момент.

С правильной информацией.

Без лишнего шума.
