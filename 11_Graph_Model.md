# Purpose

Данный документ описывает графовую модель данных Event OS.

Graph Model является фундаментом всей платформы.

Timeline.

Контекст.

Навигация.

Уведомления.

Права доступа.

ИИ.

Все эти компоненты работают поверх графа.

Граф является единственным представлением реальности внутри системы.

---

# Why Graph

Традиционные CRM строятся вокруг таблиц.

```
Client

↓

Order

↓

Task

↓

Invoice
```

Такая модель хорошо хранит данные.

Но плохо описывает реальные связи между объектами.

---

Реальное мероприятие выглядит иначе.

```
Фотограф

↓

Снимает

↓

Сцену

↓

В определенной локации

↓

В определенное время

↓

При определенной погоде

↓

Совместно с видеографом

↓

По договору

↓

Для клиента
```

Это уже не таблица.

Это сеть взаимосвязей.

---

# Event Graph

Каждый проект представляет собой ориентированный граф.

```
                Event
                  │
      ┌───────────┼────────────┐
      │           │            │
 Timeline      People     Documents
      │           │            │
    Scene       Roles        Files
      │           │            │
 Locations    Teams       Communication
      │
   Weather
```

Все вершины графа принадлежат одному событию.

---

# Nodes

Каждый объект системы является вершиной графа.

Например:

```

Weather

Equipment

Vehicle

Invoice

Document

Task
```

Новые типы узлов не должны менять архитектуру.

# Edges

Связи являются сущностями первого класса.

Примеры:

```
ASSIGNED_TO

PARTICIPATES_IN

LOCATED_AT

PRECEDES

FOLLOWS

BELONGS_TO

CREATED_BY

DEPENDS_ON

USES

DELIVERS_TO

RELATED_TO

RESPONSIBLE_FOR

HAS_STATUS

ATTACHED_TO
```

Связи имеют собственные свойства.

Например:

```
Photographer

ASSIGNED_TO

Scene

from

09:00

to

13:00
```

# Event Root

Каждый граф имеет один корневой объект.

```
Event
```

Все остальные вершины должны иметь путь к нему.

Если объект невозможно связать с Event, он не принадлежит событийному слою.

Это правило событийного слоя, а не всего ядра (Алексей, 6 октября 2026,
`BRIDGE_BRONIOS.md` §0). Объекты модулей на фундаменте — например, бронь зала
в BroniOS — живут у площадки и существуют без события. Когда студия работает
на событии, в граф входит **узел-ссылка на бронь**; сама бронь остаётся в
модуле и меняется только явной просьбой и ответом студии (правило матрёшки:
бронь — подсущность со своим временем).

# Timeline Graph

```

↓

Scene B

↓

Scene C

↓

Scene D
```

Но это только один из возможных маршрутов.

Граф допускает альтернативные сценарии.

Например.

```

↓

Rain

↓

Indoor Ceremony
```

Или

```

↓

↓

```

Timeline представляет собой предпочтительный путь через граф.

# Notification Graph

Уведомление не хранится заранее.

Оно вычисляется.

```
Object changed

↓

Graph updated

↓

Affected users

↓

Context recalculated

↓

Notification created
```

Таким образом система исключает лишние уведомления.

# Context Graph

Контекст не хранится.

Он вычисляется.

Например.

```
Photographer

+

Current Time

+

Current Scene

+

Weather

+

Latest Changes

↓

Context
```

Таким образом один и тот же граф порождает разные представления для разных пользователей.

---

# Permissions

Права доступа также вычисляются через граф.

Например.

```
Organization

↓

Project

↓

Photo Team

↓

Photographer

↓

Gallery
```

Если путь существует — доступ разрешен.

Если нет — запрещен.

---

# AI

ИИ никогда не создает собственную модель данных.

Он работает поверх существующего графа.

```
Graph

↓

Context

↓

AI Analysis

↓

Recommendation
```

ИИ не изменяет граф напрямую.

Любые изменения подтверждает пользователь.

# Design Rules

При создании новых сущностей необходимо соблюдать следующие правила.

## Every object is a node.

Любая новая сущность становится вершиной графа.

---

## Every relationship is explicit.

Любая связь описывается явно.

Не допускаются "скрытые" зависимости.

---

## Every node belongs to an Event.

Любой объект событийного слоя должен иметь путь к событию. Объекты модулей фундамента входят в граф ссылкой (см. Event Root).

---

## Every node has history.

Любое изменение сохраняется.

---

## Every node can be referenced.

Любой объект может использоваться другими объектами.

---

## Graph first.

Никакая бизнес-логика не должна обходить графовую модель.

---

## Every event is a container.

События — это контейнеры-матрёшки. Внешняя оболочка определяет рамки, внутри
подсущности (Алексей, 18 сентября 2026; правило общее для Event OS, Light Plan
и BroniOS).

- Подсущности жёстко привязаны к своему времени. Оболочка их не двигает — ни
  переносом, ни растяжкой.
- Переносить целиком можно только пустую оболочку.
- Растягивать можно и непустую: начало не позже начала первой подсущности,
  конец не раньше конца последней. Оболочка не может быть меньше содержимого,
  но может быть больше.
- События могут дробиться уже внутри самого события: подсущность — тоже
  событие со своей оболочкой. Глубина вложенности не оговаривалась.
- Точки на таймлайне — якорные. Оболочку держит только то, что привязано к
  скелету времени; «точка без привязки к скелету времени считается не
  привязанной» и содержимым не считается.

**Жёсткость подсобытий (Алексей, 6 октября 2026).** «Она подходит для событий,
в которых есть подсобытия, свадьба с загсом и фотостудией, начало можно
поменять, прогулку можно сократить или скорректировать по погоде, но время
загса "железобетонное", студия имеет свои рамки графика».

Как это уже работает в Light Plan (Алексей, 06.10, со скриншотом ленты дня):
«я могу раздвигать событие сужать, но не могу сдвинуть его выше или ниже
брони студии… внутри может быть опорная точка вроде ЗАГСА которая определит
границы, такие события как **гвоздики**». Термин платформы: **гвоздик** —
«любые события которые пригвоздили временем» (Алексей, 06.10). Любая
подсущность со временем держит оболочку — ЗАГС, бронь студии, прогулка с
часами. Так это работает в Light Plan сегодня.

Предложение на будущее, не решено и в Light Plan не сделано: у каждой подсущности есть
**хозяин времени**.
- **Внешний** — ЗАГС, студия, ресторан. Время задаёт он; изнутри события его не
  двигают, только просят (студия) или не меняют вовсе (ЗАГС).
- **Свой** — прогулка, сборы (сегодня тоже гвоздик, если у неё есть время). Организатор или фотограф правит её сам: сдвигает,
  сокращает, переносит по погоде. Но это правка самой подсущности, а не
  побочный эффект жеста над оболочкой.

Пример: свадьба 10:00–20:00, внутри ЗАГС 13:00–13:40 (внешний), студия
15:00–17:00 (внешний, бронь BroniOS), прогулка 17:30–19:30 (своя). Дождь —
прогулку сокращают до 17:30–18:30 одной правкой; начало свадьбы можно
сдвинуть на 11:00; ЗАГС и студия стоят, и оболочка не может стать уже
13:00–17:00.

Правило вскрыл календарь Light Plan: в календаре телефона событие плоское,
подсущностей у него нет, поэтому там его можно таскать как угодно. Как это
ложится на Event → Scene (`Timeline Graph`, `Scene`) — решать при разборе
`BRIDGE_LIGHT_PLAN.md` §12; что Scene и есть внутренний слой, — предположение,
не решение.

---

# Why This Matters

Большинство систем хранят данные.

Event OS хранит взаимосвязи.

Именно связи позволяют платформе понимать контекст, автоматически распространять изменения, вычислять релевантную информацию и сопровождать пользователя через событие.

---

# Graph Model Statement

> **Graph Model — это цифровое представление мероприятия, в котором каждый объект является вершиной, каждая взаимосвязь имеет явное описание, а весь пользовательский опыт строится на вычислении контекста поверх этого графа.**
