# Purpose

Данный документ описывает архитектуру Event OS на верхнем уровне.

Это не описание технологий.

Это описание логической структуры платформы, взаимосвязи компонентов и принципов их взаимодействия.

Техническая реализация (Frontend, Backend, Database, API, Infrastructure) описывается отдельно.

---

# Architectural Vision

Event OS представляет собой контекстно-ориентированную операционную систему.

Архитектура строится вокруг одного события (Event), внутри которого существуют все остальные сущности.

Главной задачей системы является не хранение данных, а вычисление актуального контекста для каждого участника проекта.

---

# Architectural Layers

```
┌──────────────────────────────────────────────┐
│                User Experience               │
├──────────────────────────────────────────────┤
│         Context Navigator / Timeline         │
├──────────────────────────────────────────────┤
│              Context Engine                  │
├──────────────────────────────────────────────┤
│               Graph Engine                   │
├──────────────────────────────────────────────┤
│            Domain Model (Event)              │
├──────────────────────────────────────────────┤
│        Storage / Sync / Infrastructure       │
└──────────────────────────────────────────────┘
```

Каждый слой имеет единственную ответственность.

---

# Core Entity

Главной сущностью платформы является **Event**.

Все остальные объекты существуют исключительно как элементы события.

```
Event
│
├── Timeline
├── Scene
├── People
├── Teams
├── Roles
├── Documents
├── Files
├── Communication
├── Finance
├── Weather
├── Locations
├── Equipment
├── Postproduction
├── History
└── Context
```

Ни одна сущность не должна существовать изолированно.

---

# Graph Architecture

Внутреннее представление проекта основано на графовой модели.

```
Photographer
        │
        │ assigned
        │
     Scene
        │
        │ located_at
        │
    Location
        │
        │ weather
        │
     Forecast
```

Любая информация вычисляется через связи между объектами.

Система никогда не хранит готовые представления.

Она вычисляет их динамически.

---

# Timeline Architecture

Timeline является визуальным представлением графа во времени.

```
08:00 ───── Scene ──────►

11:30 ───── Scene ──────►

14:00 ───── Scene ──────►

18:00 ───── Scene ──────►
```

Каждая Scene представляет собой самостоятельный контейнер контекста.

Timeline не содержит бизнес-логики.

Он является навигационной поверхностью системы.

---

# Scene

Scene — минимальная рабочая единица Event OS.

Каждая сцена объединяет все, что относится к определенному месту и моменту времени.

```
Scene

├── Time
├── Location
├── Weather
├── Participants
├── Documents
├── Chat
├── Attachments
├── Tasks
├── Equipment
├── Notes
├── History
└── Status
```

Практически любой пользователь большую часть времени взаимодействует именно со сценами.

---

# Context Engine

Context Engine — центральный вычислительный компонент платформы.

Он отвечает на вопрос:

> Что должен увидеть конкретный пользователь прямо сейчас?

Входные данные:

- граф проекта;
- текущее время;
- роль пользователя;
- текущая сцена;
- последние изменения;
- местоположение;
- состояние проекта.

Результатом является персональный рабочий контекст.

---

# Context Formula

Условно вычисление можно представить следующим образом:

```
Context =
f(
    Graph,
    Timeline,
    Scene,
    Role,
    Time,
    Location,
    State,
    History
)
```

Данная формула описывает философию системы, а не конкретный алгоритм.

---

# Navigator

Navigator является пользовательским интерфейсом Context Engine.

Он не показывает весь проект.

Он показывает следующий релевантный контекст.

По аналогии с автомобильным навигатором.

```
Current Scene

↓

Current Context

↓

Next Action

↓

Next Scene
```

---

# Domain Modules

Архитектура разделена на независимые домены.

```
Projects

People

Organizations

Timeline

Communication

Documents

Media

Finance

Postproduction

Notifications

AI

Administration
```

Каждый домен обладает собственной бизнес-логикой.

Связи между доменами строятся исключительно через граф проекта.

---

# Communication

Коммуникация не существует отдельно.

Любое сообщение принадлежит объекту.

Например:

```
Scene

↓

Chat
```

или

```
Document

↓

Discussion
```

или

```
Task

↓

Comments
```

Это исключает потерю контекста.

---

# Documents

Документы являются частью графа.

Они не существуют самостоятельно.

Каждый документ связан минимум с одним объектом.

Например:

- Event;
- Scene;
- Contractor;
- Contract;
- Invoice;
- Gallery.

---

# Media

Файлы также являются частью графовой модели.

Например:

```
RAW Files

↓

Retouch Task

↓

Edited Photos

↓

Gallery

↓

Client Delivery
```

Система хранит не только файлы, но и жизненный цикл материалов.

---

# Notifications

Уведомления никогда не создаются вручную.

Они вычисляются автоматически.

Основанием для уведомления является изменение графа.

Пример:

```
Маршрут изменился

↓

Scene обновилась

↓

Context изменился

↓

Фотограф получает уведомление

↓

Ведущий ничего не получает
```

Пользователь получает только релевантные уведомления.

---

# Organizations

Платформа поддерживает несколько организаций одновременно.

```
User

├── Agency A

├── Agency B

├── Personal Projects

└── Freelance
```

Один пользователь может участвовать в нескольких организациях.

Каждая организация имеет собственные настройки, сотрудников и проекты.

---

# Temporary Users

Архитектура должна поддерживать кратковременное участие пользователей.

Например:

- клиент;
- водитель;
- музыкант;
- подрядчик.

После завершения проекта участие автоматически завершается.

Пользователь не обязан становиться постоянным клиентом платформы.

---

# Client Applications

Платформа должна работать одинаково на различных устройствах.

```
PWA

↓

Desktop Browser

↓

Tablet

↓

Mobile Browser

↓

iOS

↓

Android
```

Главным клиентом является PWA.

Все клиенты используют единую бизнес-логику.

---

# Offline Strategy

Мобильное приложение должно сохранять доступ к критически важной информации при отсутствии сети.

Минимальный офлайн-кэш включает:

- текущий проект;
- Timeline;
- маршрут;
- контакты;
- документы текущей сцены;
- ближайшие задачи.

После восстановления соединения выполняется автоматическая синхронизация.

---

# AI Layer

ИИ расположен над доменной моделью.

```
AI

↓

Context

↓

Recommendations

↓

User
```

ИИ никогда не является источником истины.

Он анализирует существующий контекст.

При отключении ИИ архитектура платформы остается полностью работоспособной.

---

# Integration Strategy

Event OS не стремится заменить специализированные сервисы.

Платформа должна интегрироваться с внешними решениями.

Примеры:

- календари;
- прогноз погоды;
- облачные хранилища;
- фотогалереи;
- сервисы доставки клиентских материалов;
- бухгалтерские системы;
- корпоративные каталоги.

Интеграции должны быть модульными и необязательными.

---

# Architectural Rules

При разработке любого нового модуля необходимо соблюдать следующие правила:

1. Новые сущности обязательно привязываются к Event.
2. Новые связи добавляются в графовую модель.
3. Любой объект должен иметь историю изменений.
4. Любой объект должен поддерживать обсуждение.
5. Любой объект может участвовать в Timeline напрямую или косвенно.
6. Контекст вычисляется автоматически.
7. Пользователь не должен самостоятельно искать изменения.

---

# Future Scalability

Архитектура должна поддерживать развитие платформы без изменения фундаментальной модели данных.

Допустимые направления роста:

- новые типы мероприятий;
- новые профессиональные роли;
- новые организации;
- новые отрасли;
- новые AI-модули;
- новые интеграции;
- новые клиентские приложения.

При этом центральная модель **Event → Graph → Timeline → Context → Navigator** должна оставаться неизменной.

---

# Architecture Statement

Архитектура Event OS строится вокруг одного принципа:

> **Система хранит граф события, вычисляет контекст, а пользователь взаимодействует только с тем, что необходимо ему в текущий момент времени.**

Все остальные компоненты платформы являются следствием этого принципа.
