## 1. Назначение

Task — минимальная единица конкретной, назначаемой и завершаемой работы внутри Project.

Этот документ формализует Task как объект графа. Он не превращает продукт в task-менеджер — само существование Task ограничено правилами, описанными ниже.

```text
Event Lifecycle (50) → крупные стадии всего проекта
Workflow (51)         → путь роли внутри стадии
Task (52)              → конкретная единица работы внутри Workflow-стадии или вне неё
```

---

## 2. Главный принцип

> Задача существует только тогда, когда существует конкретный результат. Если результата нет — это не задача, а контекст.

Это прямое продолжение `21_Projects.md §16` и `41_Design_Principles.md §22–23`.

```text
Хорошо: «Получить финальный тайминг ресторана»
Плохо:  «Подумать о ресторане»

Хорошо: «Забрать оборудование у Bel Sound до 14:00»
Плохо:  «Не забыть про звук»
```

---

## 3. Task ≠ Context

Погода, локация, маршрут, контакт, расписание — это Context, а не Task.

```text
Плохо:
Task: "Дождь в 15:00"

Хорошо:
Context: "Дождь ожидается в 15:00"
Task (если требуется): "Подготовить запасной шатёр к 14:30"
```

Система не должна автоматически превращать любую информацию в задачу (`41_Design_Principles.md §22`).

---

## 4. Task ≠ Message

```text
Message:
«Давайте перенесём церемонию на 13:30»

Task (если возникает как следствие):
«Обновить маршрут водителя»
```

Task может порождаться сообщением, но не является сообщением. Message живёт в `24_Communication.md`; факт согласия по сообщению фиксируется как `Decision`.

---

## 5. Task ≠ Change

```text
Change:
Ceremony 13:00 → 13:30

Task (следствие Change):
«Обновить маршрут»
```

`Change` (см. `54_Changes.md`) — это мутация состояния графа. `Task` — это работа, которую нужно выполнить, иногда как реакция на Change, иногда независимо от него.

---

## 6. Task ≠ Job

`PostproductionJob` (`26_Postproduction.md §7`) — специализированный подтип Task с более узкой, производственной моделью состояний (Input/Output, версии, QA).

```text
Task — общая модель, применимая к любой работе в проекте
Job  — Task, специализированный для производственного процесса постпродакшна
```

Job наследует базовые поля Task (assignee, status, deadline) и добавляет собственные (input, output, stage, version).

---

## 7. Task как узел графа

```text
Task
├── id
├── project_id
├── scene_id          (опционально)
├── workflow_stage_id (опционально)
├── title
├── description
├── assignee          (User | Team | Role)
├── status
├── priority
├── due_at
├── created_by
├── created_at
├── completed_at
└── result
```

Task всегда принадлежит Project (`11_Graph_Model.md`, "Every node belongs to an Event/Project").

---

## 8. Task и Scene

Task может быть привязана к конкретной Scene Timeline.

```text
Scene: Photo Session
 └── Task: Подготовить реквизит к 15:00
```

Task, привязанная к Scene, наследует её время и локацию как часть своего контекста, не дублируя эти поля вручную.

---

## 9. Task и Workflow Stage

Task может принадлежать стадии Workflow (`51_Workflow.md §28`).

```text
Workflow Stage: Setup
 └── Task: Расставить стулья до 12:00
```

Task, не привязанная ни к Scene, ни к Workflow Stage, — это самостоятельная разовая задача проекта (например, административная).

---

## 10. Статусы Task

Используется тот же базовый словарь, что и для Workflow Stage и Postproduction Job — единый платформенный стандарт статусов:

```text
Waiting
Ready
In Progress
Blocked
Review
Completed
Cancelled
```

Task не вводит собственный словарь статусов.

---

## 11. Blocked

Причина блокировки должна быть структурированной, а не текстовой заметкой.

```text
Task: Забрать оборудование
Blocked reason: Поставщик не подтвердил готовность
```

---

## 12. Приоритет

```text
Critical
High
Normal
Low
```

Этот же четырёхуровневый словарь используется в `53_Notifications.md` как единый стандарт приоритета для платформы.

---

## 13. Assignment

Task может быть назначена:

```text
User
Team
Role
```

Правила назначения и переназначения идентичны `26_Postproduction.md §30–31`: сохраняются `Previous Assignee`, `New Assignee`, `Reason`, `Timestamp`.

---

## 14. Deadlines

Срок Task может быть абсолютным или относительным.

```text
Абсолютный:
due_at = 2026-08-09 14:00

Относительный:
due_at = Scene("Ceremony").starts_at - 30 minutes
```

При сдвиге опорного времени относительный срок пересчитывается автоматически (см. `26_Postproduction.md §26–27`).

---

## 15. Зависимости между Task

```text
Task: Собрать декорации
depends_on
Task: Поставщик доставил материалы
```

Если зависимость не выполнена, Task остаётся в статусе `Waiting`.

---

## 16. Кто может создать Task

```text
Организатор       → любая Task в своём проекте
Роль с правом CREATE_TASK → Task в рамках своей зоны ответственности
AI (Suggestion)    → предложение Task, требующее подтверждения человеком
Система (Automation) → Task как следствие Change, если явно сконфигурировано
```

Создание Task подчиняется тем же правилам `23_Permissions.md`, что и любой объект графа.

---

## 17. AI и Task

AI может предложить Task, но не может создать её как подтверждённую единицу работы без подтверждения ответственного человека — в соответствии с общим принципом `30_AI.md` ("AI Must Not Silently Apply Important Changes").

```text
AI Suggestion:
"Похоже, нужно обновить маршрут водителя. Создать задачу?"
[Confirm] [Dismiss]
```

---

## 18. Task не должна дублировать Workflow

Если весь процесс уже описан как последовательность стадий Workflow, не нужно создавать отдельную Task на каждый технический шаг внутри стадии.

```text
Плохо:
Task: Открыть Lightroom
Task: Экспортировать JPEG
Task: Загрузить файл

Хорошо:
Workflow Stage: Retouch (одна стадия, свой статус)
```

Task используется для конкретных, дискретных поручений, а не для декомпозиции всего производственного процесса.

---

## 19. Личные Task vs Task проекта

```text
Project Task
 → принадлежит Project, видна согласно правам

Personal Task (опционально)
 → приватная заметка пользователя, не является частью Project Graph
```

Personal Task не участвует в Context Engine и Change Propagation — это личный список пользователя, не путать с Project Task.

---

## 20. Task Chat

Как и `Job Chat` (`26_Postproduction.md §33–34`), Task может иметь собственный контекст общения.

```text
Task
 ├── Status
 ├── Description
 ├── Attachments
 └── Task Discussion   (см. 24_Communication.md)
```

---

## 21. Task и Context Engine

Context Engine показывает пользователю не все его Task сразу, а те, что релевантны текущему моменту.

```text
Context = f(..., Time, State, ...)
```

```text
За 3 дня до мероприятия:
показываются Task со сроком в ближайшие 72 часа

Во время мероприятия:
показываются только Critical и Blocked Task
```

---

## 22. Task и Navigator

Navigator показывает следующую релевантную Task, а не весь список.

```text
Плохо:
Список из 40 задач проекта

Хорошо:
Next: Забрать оборудование у Bel Sound
Due: сегодня, 14:00
```

---

## 23. Task и Change

Change может автоматически порождать Task, если это явно сконфигурировано правилом.

```text
Change: Ceremony 13:00 → 13:30
 ↓
Affected Role: Driver
 ↓
Task (авто-создание, опционально): "Обновить маршрут"
```

Автоматическое создание Task из Change должно быть прозрачным и отражено в истории (`03_Principles.md`, "Everything Has History").

---

## 24. Завершение Task

Завершение Task может требовать результата, а не только смены статуса.

```text
Task: Подготовить финальный тайминг
Result: (ссылка на документ / текст / файл)
```

Не для каждой Task результат обязателен — это определяется на уровне типа Task.

---

## 25. События Task

```text
TaskCreated
TaskAssigned
TaskStarted
TaskBlocked
TaskUnblocked
TaskCompleted
TaskCancelled
TaskReassigned
```

---

## 26. Task и однодневные пользователи

Временный исполнитель должен видеть только свои Task, без истории и без остальных задач проекта.

```text
Driver (однодневный доступ)
 → видит: свои Task на день мероприятия
 → не видит: Task других ролей, историю проекта
```

---

## 27. MVP

Минимальная реализация должна поддерживать:

1. `Task` как узел графа с базовыми полями (§7).
2. Статусы из §10.
3. Assignment на User / Team / Role.
4. Абсолютные и относительные сроки.
5. Зависимости между Task.
6. Привязку к Scene и/или Workflow Stage (опционально).
7. Task Discussion.
8. Отображение в Navigator как "следующий шаг", а не список.

---

## 28. Поздние возможности

```text
Personal Task Lists
Шаблоны повторяющихся Task по типу мероприятия
AI-предложение Task на основе Change
Автоматическое обнаружение перегрузки исполнителя по Task
Групповые Task (чек-лист внутри одной Task)
```

---

## 29. Итоговое утверждение

> **Task — не центральная модель системы и не способ описать всю работу проекта. Это узкий, дисциплинированный инструмент для тех случаев, когда действительно нужен конкретный, назначаемый, завершаемый результат — и не более того.**
