# Purpose

Реестр мест — справочник площадок: студий, банкетных залов, любых мест, где
проходит съёмка или событие. Он отвечает на один вопрос: «такое место
существует, вот его номер, вот что о нём известно и куда стучаться».

Это закрывает вторую половину пункта 1 из `TASK_MINIMAL_CORE.md` («запись: такой
ID существует, вот куда стучаться») и пункт 4 («участник из справочника, а не
по инвайту») для площадок. Для людей пункт 1 уже решён отдельно: единая система
ID по номеру телефона (решение A-009, `platform_hub:DECISIONS.md`).

Граница, которую держит документ, — **справочник против содержимого**: реестр
хранит маршрут и паспорт места; съёмки, клиентов, деньги и календарь студии он не
хранит. Реестр — не маркетплейс: каталог без ранжирования, комиссий и сделок
(`90_Roadmap.md` §22).

# Реестр и граф проекта — два разных хранилища

Вывод ядра, технический выбор: реестр не часть графа проекта (`11_Graph_Model.md`).

```
Реестр мест                 Граф проекта (событие)
(справочник, один на всех)  (свой у каждого события)

Place pl…  <────────────  PlaceRef { placeId, название на день записи }
```

- Граф хранит **узел-ссылку** на место, как он уже хранит ссылку на бронь
  (`11_Graph_Model.md`, Event Root: объекты модулей входят в граф ссылкой).
- Название и адрес в ссылке — снимок на день записи. Изменение места в реестре
  не переписывает прошлые события.
- Правило «каждый узел имеет путь к Event» к самому месту не применяется: оно
  живёт в справочнике, а не в событии. Применяется к ссылке.

Почему отдельно: место существует до любого события и переживает любой проект,
а его паспорт меняет не организатор события.

# Модель записи места

```
Place
├── placeId            номер от справочника: pl + число
├── address            здание + этаж/офис, с датой «с … по …»
├── city, timezone     поля места (город сети может быть другим)
├── names[]            название с датами; прежние остаются, поиск находит по любому
├── operatorPeriods[]  хозяин/оператор с датами:
│                        организация (ИНН, название; адреса у организации нет)
│                        люди с id и ролями (хозяин, директор, администратор)
├── contactPhone[]     контактный телефон с датами; ключом не служит
├── halls[]            номер зала внутри места, название (подпись), окна,
│                        азимут, архив вместо удаления
├── aliases[]          внешние номера (2ГИС, StudioGo, Яндекс, прежний pl+телефон):
│                        помогают найти место, ключом не служат
├── lifePeriods[]      «действует» / «закрыта» с … по …
├── catalog            не подключена · подключена · снята по просьбе (с даты)
├── verification       проверена человеком · из сбора · спорная (+ note)
└── links[]            moved_from · branch_of · duplicate_of (см. ниже)
```

Формат номера — технический выбор ядра: `pl` + число, не связанное ни с
телефоном, ни с названием, не вычисляемое и **не выдаваемое повторно**.
Поле `placeId` никогда не меняется и не переходит к другому месту.

Поля о людях (id, роли, телефон хозяина) — «персонал»: наружу из реестра они не
уходят. Публичны адрес, названия, залы с окнами и азимутом, признак проверки.

# Что считать одним местом

Правила из отчёта Алексея, закреплённые в `BRIDGE_LIGHT_PLAN.md` §13:

- Сменилось название на том же месте — то же место.
- Одно название на разных адресах — разные места (связь «филиал»).
- В одном доме разные студии не сливаются.
- Сомнительная пара («возможно, то же место») — признак `verification: спорная`,
  решает человек, не скрипт.
- Общий телефон у нескольких мест — только подсказка «возможно, один хозяин».
  Телефон не склеивает места.

# Две оси состояния

Состояние места — не одно значение, а две независимые оси. Студия может
закрыться физически и остаться в каталоге, и наоборот.

**Ось 1. Жизнь помещения.** История периодов «действует / закрыта с … по …».
Открылось снова — новый период на том же номере (хозяин и название могут быть
другими). Запись, номер, залы и брони остаются при закрытии.

**Ось 2. Присутствие в каталоге.**

| Состояние | Что значит | В отдаваемом файле |
|---|---|---|
| не подключена | запись из сбора, хозяин не заявлялся | да, с признаком проверки |
| подключена | хозяин заявил права | да |
| снята по просьбе | хозяин (или заявивший) попросил убрать | нет, остаётся призрак |

«Кандидат» — не состояние, а признак проверки (`verification`).

# Связи между местами

Три вида, записываются процессом выдачи номеров, а не фотографом:

1. **moved_from («переехала из»).** У нового места ссылка на старое с датой;
   читается и в обратную сторону («переехала в»). Цепочка A→B→C идёт по ссылкам.
   Старое место получает «закрыта с …». Это единственный случай, когда номер
   меняется: окна, свет и брони привязаны к помещению.
2. **branch_of («филиал сети»).** Отдельное место со своим номером, телефоном и
   залами. Сеть — необязательная группа, ключом не служит.
3. **duplicate_of («дубль»).** Склейка: старый номер остаётся и **продолжает
   отвечать**, переадресуя на оставшийся. Номер не исчезает и не выдаётся снова.

**Не переезд:** поправка адреса (опечатка, переименованная улица, новая нумерация
домов) и смена этажа внутри того же помещения. Номер тот же, адрес меняется как
поле с датой.

**Что видит приложение при переезде.** Сообщение «переехала: <название>,
<новый адрес>», а не «закрылась». Старые съёмки остаются на старом номере. В новую
съёмку номер нового места записывается только после подтверждения фотографа:
адрес и окна другие, молча подменять нельзя.

# Снятие по просьбе и призрак

**Снятие.** Убирает карточку из поиска и заявок и стирает данные периода хозяина:
людей и роли, клиентов, расходы, памятку, токены и подписку, календарь, фото и
тексты залов, цены. Права хозяина и администраторов закрываются датой.

**Призрак — что остаётся:** номер, адрес с этажом/офисом, названия с датами,
список залов (номера, названия, окна и азимут), связи, статус «снята с …».

**Чего в призраке нет:** людей, телефонов хозяина, клиентов, денег, фото, текстов
и цен. (Осторожный выбор по умолчанию из-за закона о персональных данных и
авторских прав; пересматривается — см. «Открыто».)

**Зачем призрак.** Прошлые съёмки и ссылки у фотографов не должны оборваться;
новый хозяин восстанавливает место под тем же номером.

**Восстановление.** Новый хозяин заявляет права: код на номер из карточки места и
почта. Место оживает под тем же номером и теми же номерами залов, период хозяина
начинается пустым. Фото, тексты, цены и клиентов прежнего хозяина он не получает.

**Спор.** Вернулся прежний хозяин до заявления нового или одновременно с ним —
спор о месте. По словам Алексея («это решаю я, у меня будет появляться
оповещение») решает он; канал оповещения не определён.

**Два слова не путать.** «Призрак» в этом документе — запись в реестре. «Фантом»
в Light Plan — копия карточки студии на телефоне фотографа; сервер ради неё
ничего не хранит. «Призраки чужих календарей» (`BRIDGE_BRONIOS.md` §1.4) —
третье, к реестру отношения не имеет.

# Хранение: два выхода, не в git

По словам Алексея («призрак хранить у меня на Яндекс сервере», «Яндекс, не в git»).
Вывод ядра, не слова Алексея: это закрытое хранилище в его Yandex Cloud.

| Что | Где | Кто читает |
|---|---|---|
| Реестр (полный, с призраками, историей, связями) | закрытое хранилище Яндекса | процесс выдачи номеров и ядро |
| Отдаваемый файл для приложений | объект в бакете Яндекса, строится из реестра | Light Plan, BroniOS, сайт |

- В отдаваемый файл попадают **все записи, кроме снятых по просьбе**, с
  признаком проверки: «проверена человеком» · «из сбора, не проверена» · «спорная».
  Только проверенные отдавать нельзя: отчёт 04.11 не проверен звонком или визитом.
- Файл **общий, а не по городу**: запрос по городу выдаёт, куда едет фотограф
  (довод Light Plan).
- Файл несёт `updatedAt` или ETag. Приложение сравнивает свою копию по номеру
  места; отдельного признака «название изменилось» не нужно.
- Призрак в отдаваемый файл не попадает.
- В репозитории остаются формат и пример, но не реальные данные.

**Ограничение, которое реестр не снимает.** Публичная ветка BroniOS
`claude/project-thread-1dq5lp` уже содержит каталоги `studio_catalog_tomsk` и
`studio_catalog_ru` (по проверке 05.11: 39 файлов, 1506 студий, без телефонов).
Название и адрес этих студий остаются в публичной истории git, снятие по просьбе
из неё не стирает. Чистка истории и удаление ветки — внешнее действие, только по
слову Алексея. Решение по ветке на момент записи: «пока не удаляем».

# Отдаваемый файл: формат версии 1

Файл `served_places.json` строит `app/tools/import_catalog.js` из реестра
(`PlaceRegistry.servedFile()` плюс шапка). Вывод ядра, не слова Алексея: формат —
договорённость между ядром и приложениями, Light Plan вправе просить поправки.

```
{
  "format": 1,
  "etag": 3348,              // растёт с каждым изменением реестра; приложение сравнивает с копией
  "asOf": "2026-11-05",      // день сборки файла
  "count": 1518,
  "places": [ Place, … ]     // по возрастанию номера
}

Place = {
  "placeId": "pl100001",       // номер места; ключ в Studio.catalogId и в записи съёмки
  "name": "Томсон",            // текущее название
  "names": [{"from","to","value"}, …],   // прежние названия с датами
  "address": "Томск, ул. …" | null,      // null = адрес при сборе не найден
  "city": "Томск",
  "timezone": "Asia/Tomsk" | null,       // null = не известен; приложение узнаёт зону по адресу само
  "halls": [{"number":1, "name":"Эдисон", "windows":true|null, "azimuth":225|null, "archived":null}, …],
  "hallsCount": 3,             // только если залов несколько, а названий нет; halls тогда пуст
  "life": "действует" | "закрыта",                       // ось 1
  "catalog": "не подключена" | "подключена",             // ось 2 («снята по просьбе» в файл не идёт)
  "verification": "проверена человеком" | "из сбора" | "спорная",
  "note": "…",                 // рабочая пометка сбора, только если есть; у «спорной» — почему
  "links": [{"type":"moved_from"|"branch_of"|"duplicate_of", "id":"pl…", "since":"…"}, …],
  "mergedInto": "pl…",         // только у склеенного дубля: старый номер ведёт на этот
  "movedTo": "pl…",            // только если место переехало
  "updatedAt": "2026-11-04"
}
```

Как читать (правила, а не формат):

- **Пустой `halls` без `hallsCount`** = у студии один зал с названием студии
  (правило Алексея 04.11, `studio_catalog_ru/README.md`, правило 1).
- **`life: "закрыта"`** — место в файле остаётся, чтобы старые съёмки находили
  его; в выборе новой студии приложение такие скрывает. Дата закрытия в
  черновике — день записи в справочник, а не настоящая дата.
- **`verification: "спорная"`** — возможный дубль или спорный адрес; скрипт места
  не склеивает, решает человек. Приложение показывает пометку, но не прячет.
- **`mergedInto`** — заменить номер в своей копии на указанный; старый номер
  продолжает отвечать.
- **Чего в файле нет:** людей, телефонов, цен, фото, внешних номеров 2ГИС и
  StudioGo (они лежат в полном реестре как `aliases`), снятых по просьбе.
- Названия залов, окна и азимут в черновике есть только у Томсона; у остальных
  залы из StudioGo, окна `null`.

# Импорт чернового справочника (05.11.2026)

`app/tools/import_catalog.js` читает файлы каталога BroniOS
(`docs/cross-project/studio_catalog_tomsk`, `studio_catalog_ru`) и заводит места
в реестр: номера выдаёт реестр (Томск первым — у Томсона `pl100001`, дальше
города по алфавиту имени файла, внутри файла по порядку записей).

- **Признаки проверки.** «Проверена человеком» — только запись, где хозяин на
  связи (`connectedToBroniOS`, сейчас один Томсон). Запись с пометкой
  «возможно, то же место, что …» или «Алексей уточнит» — «спорная». Остальные —
  «из сбора».
- **Внешние ключи.** id BroniOS и id StudioGo / 2ГИС / Gorko кладутся в `aliases`.
  По ним повторный запуск находит место и ничего не выдаёт заново: меняется
  только название и адрес (с датой). Одна карточка источника на несколько
  адресов (Саратов, «Фотостудия 2.8») получает ключ с хешем адреса.
- **Прежние названия** (`formerNames`) тоже в `aliases`: поиск по реестру их находит.
- **Не склеивается и не связывается само:** «филиал», «возможно, то же место» —
  остаются пометкой в `note`; связи `branch_of` и склейка — решение человека.
- **Телефоны** лежат у Алексея вне git (правило 8 каталога). Ключ `--phones <файлы>` связывает их с местом по внешнему ключу (`studiogo:<ID>`, `2gis:<ID>`) и пишет только в `contactPhone` закрытого `registry.json`; в отдаваемый файл они не идут, место по ним не ищется и не склеивается (один номер у нескольких мест — лишь подсказка). Запускать там, где лежат файлы телефонов (Mac Алексея), в папку вне репозитория.
- **Куда пишет.** Только в указанную папку вывода: `registry.json` (полный
  реестр) и `served_places.json`. Папка не должна быть в репозитории
  (слово Алексея: «Яндекс, не в git»). Сейчас файлы без телефонов лежат в общей папке проекта
  `place-registry/`; на Яндекс не выложены.

Запуск из `app/`: `node tools/import_catalog.js --from <папка json> --out <папка>
--date ГГГГ-ММ-ДД [--registry <registry.json прошлого запуска>]`. Проверки:
`node --test core/registry.test.js tools/import_catalog.test.js`.

# Выдача номеров

- Номера выдаёт **один процесс** (единственный писатель — урок сайта: устаревшая
  копия затирает чужие правки). Кто он — не решено.
- До ядра справочником служат файлы каталога, номера выдаёт один скрипт; ядро
  потом импортирует файл как есть.
- Номер не вычисляется на устройстве. Приложению нужна **локальная копия
  отдаваемого файла** (полевой режим §11 её и так требует).
- Старые адреса `pl` + телефон остаются как `aliases`: помогают найти место, ключом
  не служат. Ручная карточка в Light Plan находит студию поиском по адресу и
  названию; совпадение по телефону — подсказка «это та же студия?».
- Приложение хранит номер места в карточке студии и в записи съёмки. Для студии,
  заведённой фотографом вручную, номера нет — ключ карточки в приложении свой.

# Продажа студии

Номер места и номера залов не меняются. Решения Алексея (см. выше) записаны
буквально; их применение — вывод ядра:

- Остаток токенов переходит новому хозяину; список клиентов тоже; долг остаётся у
  прежнего хозяина.
- «Право переходит»: читаю как — у нового хозяина остаётся то право **предлагать**
  записи фотографу, которое было у прежнего, фотографа заново не спрашивают.
  Подтверждение каждой записи фотографом (`BRIDGE_LIGHT_PLAN.md` §3) остаётся.
  Если Алексей имел в виду запись без подтверждения, это противоречит §3 и должно
  быть сказано отдельно.
- Совет, не решение: сообщить фотографу «у студии сменился хозяин» с отзывом связи
  одним нажатием.
- Бронь хранит номер места, номер зала и снимок: название и период хозяина на
  тот день. Будущие брони, принятые прежним хозяином, новый видит как «принятые
  до вас».

# Сценарии проверки

Эти десять ситуаций станут первыми проверками кода (шаг Б). Каждая описана тем,
что должно произойти:

1. **Переименование.** Название сменилось, место то же: номер тот же, в `names`
   два имени с датами, поиск находит по обоим.
2. **Переезд.** Новое место со ссылкой `moved_from`; старое закрыто; запрос к
   старому номеру отдаёт «переехала в <новый>».
3. **Цепочка.** A→B→C: от A читается путь до C.
4. **Поправка адреса.** Опечатка или новая нумерация: номер тот же, новое значение
   адреса с датой, связи «переехала из» нет.
5. **Филиал.** Одно название на двух адресах: два номера, связь `branch_of`.
6. **Закрытие и повторное открытие.** Два периода жизни на одном номере; бронь
   в закрытый период отвергается.
7. **Снятие по просьбе.** Из отдаваемого файла запись исчезает; в реестре остаётся
   призрак без людей, телефонов, денег, фото и цен.
8. **Восстановление.** Новый хозяин получает тот же номер и те же номера залов, период хозяина пуст.
9. **Склейка дублей.** Старый номер отвечает как оставшийся; повторно не выдаётся.
10. **Сомнительная пара.** Запись со статусом «спорная» попадает в файл с признаком
    и `note`, не склеивается сама.

Отдельно проверяется, что номер не выдаётся второй раз и что обход графа проекта
с ссылкой на место не теряет связности (`Graph.orphanNodes()` пуст).

# Термины

- **Место** — здание + этаж/офис. Ключ студии в системе.
- **Реестр мест** — справочник, выдающий номера мест и хранящий их паспорт.
- **Отдаваемый файл** — выгрузка реестра для приложений, без призраков.
- **Призрак** — запись снятого места в реестре, без людей и денег.
- **Фантом** — копия карточки студии на телефоне фотографа (Light Plan).
- **Ссылка на место (PlaceRef)** — узел графа проекта: номер места + название на
  день записи.

(Статьи в `99_Glossary.md` добавятся вместе с кодом.)
