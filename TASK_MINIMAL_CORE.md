# Задача: минимальное ядро Event OS — что в него обязано войти

**Кому:** разработчику Event OS.
**Повод:** предложение Алексея (3 сентября 2026) — собрать ядро Event OS с
минимальным функционалом и подключить его к BroniOS, где ядро уже готово
(расписание, календарь, залы).

---

## Сначала — граница, которую задаёт сам BRIDGE_LIGHT_PLAN

`BRIDGE_LIGHT_PLAN.md §9`, дословно:

> **Но из этого не следует, что связь фотографа со студией идёт через Event
> OS.** Обычная студийная съёмка — портрет, предметка, тест — это топология 1
> (пункт 4): фотограф сам себе организатор, события в смысле Event OS нет
> вовсе. Если продление часа и вызов администратора потребуют участия Event OS,
> функция не заработает в самом частом случае. […] Значит каналов два, и они не
> подменяют друг друга.

Из этого следует практический вывод для порядка работ: **функция «продлить
время» через Event OS не проходит и ждать её не должна.** Она делается прямым
каналом `Light Plan ↔ BroniOS` — задача на это лежит в
`BroniOS/TASK_LIGHT_PLAN_BRIDGE.md`.

Event OS нужна для второго канала — `событие ↔ студия`, когда агентство ведёт
свадьбу и держит площадку в том же проекте. Это отдельный и более редкий
сценарий, и минимальное ядро надо считать по нему, а не по студийному часу.

**Замер состояния, чтобы не путать «ядро готово» с «ядро есть».** Каталог
`app/` — это 534 строки скелета: `core/graph.js` (149), `core/context.js` (52),
`core/seed.js` (70) и четыре ролевые страницы по 37–85 строк. Не под git, на
GitHub не запушено (`BRIDGE_LIGHT_PLAN.md`, Housekeeping). Готовое ядро — у
BroniOS, не здесь.

## Что обязано войти в минимальное ядро

Четыре пункта, и все четыре уже стоят открытыми в `BRIDGE_LIGHT_PLAN.md`.
Ядро, собранное без них, упрётся в них на второй неделе.

### 1. ID участника и головной сервер маршрутизации (пункт 1)

«Просто список аккаунтов» словами Алексея: запись «такой ID существует, вот куда
стучаться». Держать явным различие **справочник против содержимого** — маршрут
хранится, съёмки и клиенты нет.

Не решено и требует решения до кода: ID заменяет аккаунты полностью, дополняет
их лёгким слоем, или относится только к временным ролям, а Organizer/Client
проходят обычную регистрацию.

### 2. Граф приглашений произвольной глубины (пункт 4, сценарий 3)

Приглашения рекурсивны: фотограф, сам приглашённый агентством, приглашает своего
ассистента отдельным инвайтом, о котором агентство не обязано знать. Плоский
список участников проекта этого не выражает. Нужен граф с произвольной глубиной
и явное правило, кто видит чужую ветку.

### 3. Согласие адресата перед записью в его данные (пункт 3)

Организатор заполняет карточку в календаре фотографа напрямую.
`23_Permissions.md` даёт `ASSIGN`/`INVITE`/`RW`, но не оговаривает, нужно ли
подтверждение адресата. Для Light Plan это не мелочь: принцип «приложение не
пишет данные пользователя без его действия» там не нарушался ни разу, и это
будет первый случай.

**Тот же вопрос приходит со стороны студии** (пункт 9): «администраторы сообщают
в Light Plan информацию» — та же чужая рука в данных фотографа. Ответ должен
быть один на оба случая, иначе в Light Plan окажутся два разных правила для
одного действия.

### 4. Участник из справочника, а не по инвайту (пункт 9)

Роль `Venue Manager` уже описана в `22_Roles.md §12.1` — заводить нечего. Новое
— **способ попадания в проект**: студия существовала до всякого проекта и
приходит из внешнего справочника. Фаза 13 роадмапа знает `shared contractors` со
стороны агентства; здесь то же самое со стороны подрядчика.

## Чего в минимальное ядро НЕ входит

- **Переговорная пара «запрос — ответ» со сроком.** `53_Notifications.md §14`
  описывает доставку (Push, In-App, Navigator Only, Timeline, Email), но не
  запрос с дедлайном, где молчание значит «нет». Это нужно продлению — а
  продление идёт прямым каналом, минуя Event OS. Заводить механизм в ядре
  заранее не нужно; вернуться к нему, когда появится сценарий `событие ↔ студия`.
- **Адрес организации.** Пункт 6 закрыт: юрлицу нельзя ничего отправить,
  дозываются человека при ней. Контрагенты описываются, а не адресуются.
- **Marketplace.** `90_Roadmap.md §22`, запрет в силе.
