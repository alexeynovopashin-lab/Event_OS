## 2. Как устроен модуль (общий контракт)

Это мой вывод, а не решение: один и тот же шаблон для каждого модуля, чтобы приложение «брало готовое».

Модуль состоит из шести частей:

1. **Схема данных.** Файл JSON с версией (`v1`, `v2`…). Это главный документ модуля: его читают и web, и Swift.
2. **Правила.** Чистые функции без экрана: «как склеить клиента по номеру», «когда пора напомнить». Одинаковый результат в web и Swift.
3. **Общие проверочные данные.** Набор «вход → ожидаемый результат», по которому проверяют обе реализации. Если web и Swift дают разные ответы, ломается проверка, а не клиент. Образец уже есть: в Light Plan `make parity` строит `Fixtures/` из web-беты и сверяет Swift [факт, `LightPlan/CLAUDE.md`].
4. **Хранилище (адаптер).** Модуль не знает, где лежат данные: файл на телефоне, IndexedDB в браузере, сервер. Приложение подставляет свой адаптер.
5. **Экран.** Web: готовый компонент (веб-компонент, один файл со своими стилями). Swift: готовый SwiftUI-вид. Экран можно не брать, если приложению нужны только правила и данные.
6. **Крючки.** Что модуль отдаёт наружу (события: «время съёмки изменилось»), что спрашивает у приложения (согласие на запись в чужие данные, BRIDGE §3), как ведёт себя без сети.

Честное ограничение [вывод]: «писать один раз» работает для частей 1–3 (схема, правила, проверочные данные). Экран и хранилище в web и Swift придётся делать дважды. Один код на обе платформы не получится: Swift-версия Light Plan сознательно строится отдельно от web-беты, истории репозиториев разделены (`LightPlan/CLAUDE.md`). Это делает контракт важнее кода.

## 3. Каталог модулей

Состояние Light Plan — по папкам `LightPlan/Packages/` и `LightPlan/CLAUDE.md` (названия файлов, код не читал построчно). Состояние BroniOS — по `BroniOS/ROADMAP.md`, `HANDOFF.md`, `docs/core/BroniOS_core_requirements.md`. Состояние ядра — по `Event_OS/app/` и документам.

### 3.0. Граф связей
- **Что это.** Узлы (событие, человек, место, документ…) и связи между ними; из графа считается, что кому показать (`11_Graph_Model.md`, `12_Context_Engine.md`).
- **Где есть.** Ядро: `app/core/graph.js` (287 строк), `context.js` (61), `seed.js` (160) [факт]. Слова Алексея: «У нас также уже есть система связей на графах». В Light Plan графа как отдельной части нет: связи идут по номерам (`Session.clientId`, `Studio.catalogId`, `LightPlan/CLAUDE.md`) [факт].
- **Дописать.** Схему данных графа в виде JSON `v1`; выгрузку графа с телефона; правило «кто видит чужую ветку» (TASK_MINIMAL_CORE п.2, граф приглашений).
- **Контракт.** Модуль-основа: все остальные кладут в него свои узлы. Приложение не обязано хранить весь граф: берёт свою часть.

### 3.1. ID человека и вход
- **Что это.** Один человек = один ID по номеру телефона, код подтверждения по почте или в Telegram.
- **Где есть.** Решено: A-009 08.10, 09.10 («телеграм не всегда доступен, лучше код присылать по почти или телеграм») [решено, `platform_hub:QUEUE/eventos.md`, Q-015]. Код: `app/core/id.js`, функция `appId()` (28 строк); правила нормализации номера — в Light Plan (`TelCountry`: 27 строк web плюс 217 стран из libphonenumber, `LightPlan/CLAUDE.md`) [факт]. Сервера входа нет [не проверено полностью].
- **Дописать.** Сервер подтверждения номера; общий модуль нормализации номера (сейчас живёт в Light Plan, ядро ссылается на него в комментарии).
- **Контракт.** `phoneKey(raw) → "id<номер>"`; `verify(id, code) → пропуск устройства`. Ничего не доказывает по одному ID (BRIDGE_LIGHT_PLAN §1).

### 3.2. Люди: адресная книга, клиенты, контакты

Если Алексей имел в виду другое разделение, скажет.

- **Контракт.** `Person` (имя, телефоны, мессенджеры, дни рождения), правила склейки («два совпадения из трёх» — Алексей 23.10, `LightPlan/CLAUDE.md`, К3б), адаптер «книга телефона».

### 3.3. Места и карта
- **Что это.** Реестр мест (номер места выдаёт реестр, не телефон) и карта с точками, маршрутом, поворотом по компасу.

### 3.6. Погода

- **Где есть.** Light Plan: `Data/Weather/` (запрос, хранилище, прокси, фоновое обновление), «Прогноз изменился» (30.6) [факт]. Ядро: слой Timeline (`13`), вход для ИИ (`30_AI.md`), «прогноз» как необязательная интеграция (`10_Architecture.md`) [факт].

## 6. Вопрос Алексею: слово «CRM» и North Star

Слова Алексея: «Нам нужно наше ядро-CRM». `00_North_Star.md` говорит: «Мы не создаем CRM». В North Star уже есть оговорка (6.10.2026): строки «не CRM, не ERP» относятся к событийному слою, а модули продуктов живут на фундаменте рядом с ним. Адресная книга, клиенты и чат из твоего списка — как раз общий слой, не событийный.

Варианты:

1. **Оставить «не CRM», набор называть «модулями платформы».** Что будет: North Star не меняется; в документах пишем «модули платформы», внутри них могут быть клиенты и контакты. Плюс: ничего не переписываем, слово не задевает прежние решения. Минус: снаружи (студиям, инвесторам) продукт всё равно будут называть CRM, пока не объяснишь.
2. **Переписать North Star: платформа включает CRM-слой.** Что будет: правим «Мы не создаем CRM», `01_Vision`, `02_Product_Strategy`, глоссарий. Плюс: слова и документы совпадают. Минус: ты сам записал «не CRM, не Task Manager» как защиту от размывания; сдвинется всё, что с этим согласовано (роадмап MVP, «чего не должно быть в MVP»).
3. **Вынести CRM-слой отдельным продуктом на тех же модулях.** Что будет: Event OS остаётся событийным, CRM — отдельное приложение на общем наборе модулей. Плюс: чистые границы. Минус: ещё один продукт и ещё один набор экранов, раньше времени.

**Мой совет: вариант 1.** Твой список (адресная книга, чат, карта, файлы) нужен на фундаменте, а North Star это уже разрешает в «Двух этажах». Менять формулировку незачем; решение можно вернуть позже, когда станет ясно, что студиям нужен именно «CRM-продукт». Это совет, не решение. Файл North Star я не трогал.

Остальные открытые развилки (где живёт код модулей, где лежат сообщения, кто видит рецепт, нужен ли калькулятор в ядре) остаются без ответа с 04.11; по ним совет прежний: код модулей — в отдельной папке репозитория, сообщения — на сервере с сроком хранения, рецепт — как отдельное приложение [вывод, не решение].
