## 2. Как устроен модуль (общий контракт)

Это мой вывод, а не решение: один и тот же шаблон для каждого модуля, чтобы приложение «брало готовое».

Модуль состоит из шести частей:

1. **Схема данных.** Файл JSON с версией (`v1`, `v2`…). Это главный документ модуля: его читают и web, и Swift.
2. **Правила.** Чистые функции без экрана: «как склеить клиента по номеру», «когда пора напомнить». Одинаковый результат в web и Swift.
3. **Общие проверочные данные.** Набор «вход → ожидаемый результат», по которому проверяют обе реализации. Если web и Swift дают разные ответы, ломается проверка, а не клиент. Образец уже есть: в Light Plan `make parity` строит `Fixtures/` из web-беты и сверяет Swift [факт, `LightPlan/CLAUDE.md`].
4. **Хранилище (адаптер).** Модуль не знает, где лежат данные: файл на телефоне, IndexedDB в браузере, сервер. Приложение подставляет свой адаптер.
5. **Экран.** Web: готовый компонент (веб-компонент, один файл со своими стилями). Swift: готовый SwiftUI-вид. Экран можно не брать, если приложению нужны только правила и данные.
6. **Крючки.** Что модуль отдаёт наружу (события: «время съёмки изменилось»), что спрашивает у приложения (согласие на запись в чужие данные, BRIDGE §3), как ведёт себя без сети.

Честное ограничение [вывод]: «писать один раз» работает для частей 1–3 (схема, правила, проверочные данные). Экран и хранилище в web и Swift придётся делать дважды. Один код на обе платформы не получится: Swift-версия Light Plan сознательно строится отдельно от web-беты, истории репозиториев разделены (`LightPlan/CLAUDE.md`). Это делает контракт важнее кода.

## 3. Каталог модулей

Состояние Light Plan — по папкам `LightPlan/Packages/` и `LightPlan/CLAUDE.md` (названия файлов, код не читал построчно). Состояние BroniOS — по `BroniOS/ROADMAP.md`, `HANDOFF.md`, `docs/core/BroniOS_core_requirements.md`. Состояние ядра — по `Event_OS/app/` и документам.

### 3.0. Граф связей
- **Что это.** Узлы (событие, человек, место, документ…) и связи между ними; из графа считается, что кому показать (`11_Graph_Model.md`, `12_Context_Engine.md`).
- **Где есть.** Ядро: `app/core/graph.js` (287 строк), `context.js` (61), `seed.js` (160) [факт]. Слова Алексея: «У нас также уже есть система связей на графах». В Light Plan графа как отдельной части нет: связи идут по номерам (`Session.clientId`, `Studio.catalogId`, `LightPlan/CLAUDE.md`) [факт].
- **Дописать.** Схему данных графа в виде JSON `v1`; выгрузку графа с телефона; правило «кто видит чужую ветку» (TASK_MINIMAL_CORE п.2, граф приглашений).
- **Контракт.** Модуль-основа: все остальные кладут в него свои узлы. Приложение не обязано хранить весь граф: берёт свою часть.

### 3.1. ID человека и вход
- **Что это.** Один человек = один ID по номеру телефона, код подтверждения по почте или в Telegram.
- **Где есть.** Решено: A-009 08.10, 09.10 («телеграм не всегда доступен, лучше код присылать по почти или телеграм») [решено, `platform_hub:QUEUE/eventos.md`, Q-015]. Код: `app/core/id.js`, функция `appId()` (28 строк); правила нормализации номера — в Light Plan (`TelCountry`: 27 строк web плюс 217 стран из libphonenumber, `LightPlan/CLAUDE.md`) [факт]. Сервера входа нет [не проверено полностью].
- **Дописать.** Сервер подтверждения номера; общий модуль нормализации номера (сейчас живёт в Light Plan, ядро ссылается на него в комментарии).
- **Контракт.** `phoneKey(raw) → "id<номер>"`; `verify(id, code) → пропуск устройства`. Ничего не доказывает по одному ID (BRIDGE_LIGHT_PLAN §1).

### 3.2. Люди: адресная книга, клиенты, контакты

Если Алексей имел в виду другое разделение, скажет.
- **Где есть.** Light Plan: `ClientBook`, `ClientCard`, `ClientReach` (мессенджеры, ★ основной), `ClientContacts` (запись в «Контакты» iPhone), `OrgBook`, `Greetings`, `PhoneBook`, `Records/Client.swift`, `ContactVia.swift` [факт]. - **Дописать.** Единая схема «человек» для трёх проектов (сейчас у каждого своя, раздел 5.2); зеркало контактов телефона в web невозможно так же, как в Swift [вывод, не проверено] — нужен адаптер «импорт из файла/vCard».
- **Контракт.** `Person` (имя, телефоны, мессенджеры, дни рождения), правила склейки («два совпадения из трёх» — Алексей 23.10, `LightPlan/CLAUDE.md`, К3б), адаптер «книга телефона».

### 3.3. Места и карта
- **Что это.** Реестр мест (номер места выдаёт реестр, не телефон) и карта с точками, маршрутом, поворотом по компасу.

Карта: Light Plan, `Screens/Map` (MapLibre на iPhone, MapKit на Mac; вся работа с картой в одном модуле `LightPlanMapCanvas`) [факт, `CLAUDE.md`]. Поиск и сохранённые точки: `Data/Location/` [факт].
- **Дописать.** Web-карта как компонент (в Swift карта привязана к MapLibre/MapKit; web-версия — отдельно, не проверено, что есть в замороженной web-бете); где живут «призраки» удалённых студий (Алексей 05.11: «призрак хранить у меня на Яндекс сервере», развёртывания нет).

### 3.6. Погода
- **Что это.** Прогноз на точку и час, пометка «погода изменилась», слой в расписании.
- **Где есть.** Light Plan: `Data/Weather/` (запрос, хранилище, прокси, фоновое обновление), «Прогноз изменился» (30.6) [факт]. Ядро: слой Timeline (`13`), вход для ИИ (`30_AI.md`), «прогноз» как необязательная интеграция (`10_Architecture.md`) [факт].
- **Дописать.** Источник данных и кто платит/ограничен лимитами (WeatherKit на бесплатной команде Apple не работает, `CLAUDE.md`); вынос прокси в общий сервис.
- **Контракт.** `forecast(place, from, to)`, `changed(prev, next) → список`; общее правило «что считать изменением» (`WeatherWatch`, Domain).

### 6.2. Чего Light Plan продиктовать не может

Причина одна и та же [вывод]: Light Plan — клиент одного человека на одном телефоне. Он видит только своего фотографа и работает без сервера. Всё, что нужно двум людям или двум приложениям сразу, он не «почувствует» на себе.

| Что нужно | Почему клиент этого не покажет |
|---|---|
| **Чат** | В Light Plan его нет (слова Алексея). Требования идут от BroniOS и событий, а не от фотографа |
| **Файлы на сервере с правами** | В Light Plan файлы лежат на телефоне (`Data/Store`). «Видят студия и клиент» нужно BroniOS (чеки) и сайту (фото) |
| **Согласие как механизм между людьми** | Решено на бумаге, но проверить его можно только когда пишет второй человек: организатор, студия |
| **Общий «человек»** | У Light Plan свой клиент, у BroniOS свой постоянный клиент, у события свой участник (раздел 5.2). Каждый клиент считает свою запись верной |
| **Роли организатор, водитель, клиент** | Light Plan — только роль фотографа |
| **Синхронизация между устройствами и людьми** | Light Plan хранит файл на телефоне; облако Apple на бесплатной команде недоступно (`LightPlan/CLAUDE.md`) |
| **Общий каталог и статистика студии** | Нужны студии и сайту, не фотографу |
| **Права студии (хозяин, директор, администратор)** | Нужны BroniOS и админке сайта |

### 6.3. Требования ядра, которые надо задать заранее

Это предложение [вывод]: если задать их до того, как BroniOS и события начнут брать модули, клиенты не разойдутся так, как разошлись «человек» и календарь. Каждое проверяется один раз, на модуле, а не на экране.

1. **Идентификаторы выдаёт ядро.** ID человека, номер места, номер записи (брони, документа, сообщения). Приложение хранит их, не придумывает свои.
2. **Неизвестные поля не теряются.** Приложение, получив запись с полем, которого не знает, сохраняет его и отдаёт обратно. Причина — факт: web-бета Light Plan сейчас стирает ключи, которых не знает (`Client`, `via`, `weekStart`, `LightPlan/CLAUDE.md`).
3. **Каждая запись несёт версию схемы, время изменения и источник.** Нужно для слияния, журнала и «призраков» (Q-046).
4. **Время — момент со смещением плюс часовой пояс места.** Стенные часы без зоны не принимаются (Q-002).
5. **Одно правило согласия.** Запись в чужие данные — только после ответа адресата. Один ответ на оба канала (Light Plan ↔ BroniOS и событие ↔ студия), `TASK_MINIMAL_CORE.md` п.3.
6. **Без сети — объявленное поведение.** Каждый модуль пишет в контракте: что работает без сети, что ставится в очередь, как сливается при возврате. Правило слияния «последнее изменение плюс отпечаток» берём из Light Plan 30.4, остальное не найдено (не проверено).
7. **Доставка без push.** Модуль, которому нужен сигнал, обязан иметь запасной путь: опрос при открытой карточке, локальное уведомление, письмо или Telegram. Push — улучшение, не основа.
8. **Модуль приходит с проверочными данными.** Без «вход → ожидаемый результат» модуль в ядро не принимается. Web и Swift сверяются с ними, а не друг с другом.
9. **Совместимость версий.** Старое приложение продолжает работать после выхода новой версии модуля (адреса `/v1/`). Особенно важно: сборки Light Plan на бесплатной команде живут 7 дней, веб-бета заморожена.
10. **Минимум персональных данных.** Номера, имена и ключи не попадают в публичный репозиторий и логи; удалённые студии хранятся на сервере Алексея (его слова 05.11: «призрак хранить у меня на Яндекс сервере»).
11. **Правило приёмки в ядро.** Модуль входит в ядро, когда у него два клиента или когда его нельзя сделать внутри одного клиента (чат, файлы с правами, согласие, общий «человек»). Остальное остаётся в приложении, пока второго клиента нет [вывод, предложение].

### 6.4. С чего начать

[вывод] Порядок по принципу «сначала то, на чём клиенты уже расходятся»: общий «человек» и ID (3.1, 3.2), согласие и права (3.10), файлы на сервере (3.8), чат (3.7), сигнал синхронизации (3.14).
