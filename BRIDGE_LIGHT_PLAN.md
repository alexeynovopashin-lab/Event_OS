**Назначение:** живой список находок из работы над Light Plan, которые
касаются архитектуры Event OS. Не архитектурный документ сам по себе —
очередь того, что нужно свести в сами документы (`00`–`99`), когда работа
над Event OS возобновится. Завёлся 23 августа 2026, потому что работа над

и эти детали иначе разошлись бы по коммитам другого репозитория, не
возвращаясь обратно.

для каждого решить — обновляет существующий документ, требует нового, или
уже учтён. Разобранный пункт — либо решение переезжает в `N_Doc.md`, и
пункт вычёркивается отсюда, либо остаётся с пометкой «отклонено, потому
что…». Файл не предназначен жить вечно как справочник — это очередь работы,
а не архив.

## Открыто

### 1. ID вместо аккаунта — РЕШЕНО (3 сентября 2026)
Свежая идея Алексея (23 августа 2026, не проверена): каждое приложение
(каждая установка Light Plan, каждый экземпляр роли) получает собственный
ID вместо логина/пароля — «самое дешёвое решение». Расходится с
`90_Roadmap.md`, фаза Foundation, которая называет `authentication;
organizations; users` частью ядра с самого начала. Стояло не решено: ID
заменяет аккаунты полностью, дополняет их лёгким слоем поверх, или относится
только к временным/лёгким ролям (driver, приглашённый фотограф), а
Organizer/Client всё равно проходят обычную регистрацию.

**Уточнение (см. пункт 4, сценарий 3):** приглашения рекурсивны — фотограф,
сам приглашённый агентством, может пригласить своего ассистента отдельным
инвайтом, о котором агентство не обязано знать. Значит ID/граф приглашений
не может быть плоским списком «кто кого позвал на этот проект» — нужна
произвольная глубина и явное решение, кто вообще видит чужую ветку графа
(вопрос уже поднят в `23_Permissions.md`, но не для этого случая конкретно).

**Решение: второй вариант — лёгкий слой поверх аккаунтов, с ленивым
заведением аккаунта.** `90_Roadmap.md`, фаза Foundation, не переписывается:
`authentication`, `organizations`, `users` остаются как были.

Граница, которую нужно держать дословно, иначе через месяц прочтётся как
«оба механизма зачем-то есть»: **ID адресует, аккаунт удостоверяет.** Разные
задачи, одна не подменяет другую.
- аккаунт нужен, чтобы **держать данные** — рабочее пространство, проект,
  содержимое;
- ID достаточно, чтобы **быть дозванным и дозваться**.

Водителю на один день аккаунт не нужен — нужен адрес. Захотел свой таймлайн,
который переживёт этот день, — нужен аккаунт. Отсюда: аккаунт заводится
лениво, в момент первой настоящей нужды держать данные, а не на входе. Лёгкий
участник живёт с одним ID сколько угодно — это не третий вариант («только
временные роли»), а второй с ленивым созданием: «самое дешёвое решение» в нём
уцелело целиком, и никакого второго набора правил для «лёгких» ролей заводить
не нужно.

Почему не «ID заменяет аккаунты полностью»: `appId(phone)` = `"id" +`
нормализованный номер — вычисляется любым, кто знает номер. Это адрес, а не
удостоверение: знающий номер стал бы владельцем. Заменить аккаунты ID смог бы,
только став ключевой парой с секретом на устройстве, — а это уже не «самое
дешёвое решение», ради которого идея заводилась.

Почему не «только временные роли» как отдельное третье решение: ломается о
рекурсию из уточнения выше. Фотограф в топологии 3 (пункт 4) — приглашён
агентством, лёгкий участник; он же в топологии 1 — сам себе организатор,
с полным приложением и всеми своими данными. Один человек оказывается то
лёгким, то полным в зависимости от того, кто его позвал. Идентичность,
меняющаяся от чужого действия, — плохая идентичность. Ленивое заведение
аккаунта внутри второго варианта снимает это: роль не определяет, есть ли
аккаунт, определяет факт «понадобилось держать данные».

**Правило, обязательное к соблюдению в коде: ID никогда не служит
доказательством. Он маршрутизирует и ничего не авторизует.**

Подтверждение из практики, а не из рассуждения: связь Light Plan со студией
(3 сентября 2026, Light Plan `DECISIONS.md`, «Связь со студией опознаётся по
совпадению номеров» и «Один ID на обе системы, и чего из него не следует»)
заработала при нуле регистраций. Студии не нужно удостоверять фотографа — ей
нужно его дозваться, а право продлить бронь дало совпадение номера с бронью,
а не удостоверение личности. Адресация без аккаунтов работает; авторизация
без аккаунтов — нет.

Перевыдача номера оператором остаётся открытой (см. пункт 6 этого файла) —
при этом решении она безопаснее, чем была бы при «ID заменяет аккаунты»:
перевыданный номер отдаёт постороннему чужой адрес, но не доступ к данным —
их держит аккаунт.

**Префикс схемы расширен (см. пункт 9 ниже).** `appId(phone)` до сих пор
знал один префикс — `id` для людей. Площадки (студии, банкетные залы)
получают второй, общий на все типы места — `pl` (`pl79618878078`), не по
типу площадки: рубрика — атрибут карточки, не часть адреса, иначе ломается
воспроизводимость (см. разбор в пункте 9). Схема — `<префикс><нормализованный
мобильный номер>`, префикс кодирует **класс адресуемой сущности**
(человек/площадка), не подкатегорию внутри класса.

### 2. Модель «зависимая карточка» для команды фотографов — РЕШЕНО (3 сентября 2026)
Сценарий из Light Plan: у съёмки может быть до ~10 независимых «лидеров»
(Lead Photographer), у каждого своя карточка по своему ID. У «ведомых»
(Second Photographer, Assistant) — тоже своя карточка, но с зависимостью от
того лидера, за которым они следуют, и с собственным маршрутом, который
может расходиться с маршрутом лидера. `11_Graph_Model.md` даёт общие рёбра
(в духе `DEPENDS_ON`), которые это умеют выразить в принципе, но конкретного
паттерна «карточка следует за карточкой» нет. Стояло не решено: заводить
отдельный тип ребра или готового `DEPENDS_ON` достаточно.

**Решение: `DEPENDS_ON` достаточно, новый тип ребра не нужен.** Следствие
решения по пункту 4 ниже: ответ Алексея на вопрос «что агентство не обязано
видеть про ассистента» — «ассистент — это компетенция фотографа, у него нет
отношений с организатором, в противном случае это фотограф №2» — описывает
ровно семантику `DEPENDS_ON`: ведомый привязан к тому, за кем следует, а не
к проекту напрямую. Заводить отдельный тип ребра означало бы кодировать в
самой связи что-то, чего в ней нет, — граф уже умеет это выразить.

### 3. Согласие фотографа перед записью организатором — РЕШЕНО (3 сентября 2026)
Сценарий: организатор заполняет карточку на дату в календаре фотографа
напрямую, без действия со стороны самого фотографа. `23_Permissions.md`
даёт организатору `ASSIGN`/`INVITE`/`RW` на таймлайн, но не оговаривает
явно, нужно ли подтверждение адресата прежде, чем запись состоится. Для
Light Plan это не мелочь: там принцип «приложение не пишет данные
пользователя без его действия» пока не нарушался ни разу, и это будет
первый случай.

**Решение: да, подтверждение нужно всегда, без исключений.**
`ASSIGN`/`INVITE`/`RW` в `23_Permissions.md` дают организатору право
**предложить** запись, не право записать напрямую. Запись возникает в
состоянии ожидания (`draft`/`pending`) и применяется только после действия
адресата — принцип Light Plan «приложение не пишет данные пользователя без
его действия» не нарушается этим первым случаем, а распространяется на него
без исключения.

**Тот же ответ закрывает пункт 9.** «Администраторы сообщают в Light Plan
информацию» (пункт 9 ниже) — та же чужая рука в данных фотографа, что и у
организатора. Правило одно на оба случая: и организатор, и студия могут
только предложить запись; она применяется лишь после подтверждения адресата.
Двух разных правил для одного действия в Light Plan не будет.

Следствие для реализации (см. `app/core/graph.js` — `updateNode()` сейчас
применяет запись сразу и создаёт `Change` со `status: "Applied"` без стадии
ожидания): записи, инициированные не владельцем данных, нуждаются в
промежуточном статусе на самом узле или `Change` — код это пока не умеет,
скелет писать напрямую не годится без этой доработки.

### 4. Три топологии — Light Plan не всегда центр
`app/organizer/index.html` (4 августа 2026) говорит «Organizer = Light
Plan» — весь функционал организатора живёт в Light Plan, отдельного
приложения нет. Алексей 23 августа сначала расширил это (организатор может
быть менеджером агентства ИЛИ самой невестой — для невест планируется
отдельное приложение, условно «WedPlan», пока только замысел, без кода и
без имени в проекте), а затем дал три конкретных сценария, которые стоит
считать окончательным уточнением этой находки:

1. **Фотограф независим.** Работает без Event OS вовсе — записывает всё
   со слов невесты на встрече, ведёт съёмку по своей карточке. Базовый
   минимум, то, что Light Plan умеет уже сегодня. Здесь `Organizer = Light
   Plan` буквально верно: фотограф и есть организатор своего проекта.
2. **Невеста — организатор, Light Plan — гость.** Невеста и её ближний круг
   (жених, подруга) ведут свадьбу сами в своём приложении («WedPlan»);
   фотограф остаётся у себя в Light Plan, и невеста приглашает его в свой
   кабинет по ID. Light Plan не становится частью чужого приложения — два
   приложения, один граф, соединение по ID (см. пункт 1).
3. **Агентство — организатор, Light Plan — ведомый.** Агентство ведёт всю
   свадьбу целиком и само рассылает инвайты — невесте, фотографу,
   ассистенту, водителю, кондитеру. Здесь Light Plan подчинён чужой
   иерархии, а не центр. **Осложнение, которое стоит закрепить отдельно —
   РЕШЕНО (3 сентября 2026):** фотограф может выслать свой собственный
   инвайт ассистенту — агентство об этом может не знать вовсе. Значит граф
   приглашений не двухуровневый («агентство → все остальные»), а
   рекурсивный: любой приглашённый может сам стать приглашающим для своей
   ветки, и верхний уровень не обязан видеть эту ветку целиком. Это
   требование к самому механизму ID/инвайта (пункт 1), а не только к роли
   Organizer — обычный «плоский» список участников проекта его не выразит,
   нужен граф с произвольной глубиной.

   **Решение, что именно агентство не обязано видеть:** «ассистент — это
   компетенция фотографа, у него нет отношений с организатором, в
   противном случае это фотограф №2» (Алексей). Не частичная видимость и не
   право доступа, ограниченное глубиной обхода, — структурное отсутствие
   связи: в графе просто нет ребра между ассистентом и агентством/
   организатором, только `DEPENDS_ON` до фотографа (см. решение пункта 2
   выше). Если роль должна быть видна агентству напрямую — это уже другая
   роль с собственным прямым приглашением от агентства («фотограф №2»), а
   не зависимый участник чьей-то ветки. Отсюда следствие для видимости
   `Change`: она по-прежнему идёт через фактическое участие в сценах
   (`ASSIGNED_TO`/`PARTICIPATES_IN`), как уже устроено в `context.js` — цепочка
   `DEPENDS_ON` сама по себе доступа не даёт и не должна использоваться
   как путь для запросов, идущих от организатора.

   Реализовано в скелете: `app/core/seed.js` — `person-assistant` зависит
   (`DEPENDS_ON`) от `person-photographer`, `person-second-assistant`
   зависит от `person-assistant` (глубина 2, без специального кода под
   каждый уровень — свойство самого графа). Ни у одного из них нет ребра к
   `person-organizer`. `Graph.dependentsOf()` обходит цепочку рекурсивно.

`Organizer = Light Plan` верно только для случая 1. Для случаев 2 и 3
Light Plan — участник чужого графа, не его владелец. `organizer/` в `app/`,
похоже, описывал только случай 1 — перечитать вместе с `90_Roadmap.md`
и решить, нужна ли отдельная роль/оболочка для случаев 2–3, или разница
целиком выражается правами в графе.

### 5. «Механическая ссылка» — канал доставки, которого нет в 53_Notifications.md
Приём из другого проекта Алексея: данные кодируются в компактный код или
ссылку, передаются любым существующим каналом (мессенджер, файл, вставка),

### 6. ID организации — адрес человека не годится в личность контрагента
Light Plan разбирал `appId` — единственный ID, который система сегодня умеет
считать, из мобильного номера (`"id" + telFull(phone)`), и он существует
только у владельца приложения. У организации-заказчика похожего адреса нет
вовсе: поле `id` в её записи — внутренний ключ, наружу не выходит.

Алексей попробовал наивный перенос той же схемы на организацию —
`appId(org.phone)` — и сам же нашёл, почему это не работает: телефон
контактного лица работает адресом человека и не работает личностью
контрагента. Его пример (29 августа 2026): маркетолог Анна с одним номером —
контакт ИП Ивановой по одному проекту, контакт ООО «Ромашка» по другому,
частный заказчик собственной фотосессии и заказчик Ведущего у четвёртого
клиента внутри Event OS. Один номер, четыре отношения, три разных
контрагента. `appId(org.phone)` дал бы ООО «Ромашка» и не связанному с ним
ООО «Тюльпан» **один и тот же** ID, если у них общий менеджер.

**Уточнение направления, тем же днём:** цель — обратная тому, что решает ID
человека. Для человека нужна уникальность (один номер — один адрес, разные
люди не должны схлопнуться). Для организации нужна **воспроизводимость**:
одна и та же организация, заведённая независимо в разных установках Light
Plan (или другой ролевой карточкой Event OS), должна получать **один и тот
же** ID без обмена данными между сторонами — иначе два узла графа, говорящие
об одном контрагенте, никогда не опознают друг друга. Отсюда решение идти
от **названия или ИНН**, а не от телефона представителя: это атрибуты самой
организации, не человека при ней.

**Решено тем же днём, и решение отменяет саму постановку.** Разбор шёл до
конца и вывернулся: **организация не получает адреса вовсе** — ни выведенного
из ИНН, ни назначенного Light Plan.

Довод, который решил, — свойство сущности, а не удобство: **юрлицу нельзя
ничего отправить.** Сообщение, приглашение, карточка, уведомление всегда
приходят человеку; ООО не установит приложение и не подтвердит номер. Адрес
нужен, чтобы дозваться, а организацию не дозываются — дозываются человека при
ней. Значит адрес организации решает несуществующую задачу.

Подтверждается мировой практикой: три системы, решающие опознание юрлиц
глобально (LEI по ISO 17442, DUNS, национальные налоговые номера), — все
**назначаемые держателем реестра**, ни одна не вычисляется участником. В CRM и
платёжных системах у компании непрозрачный внутренний ID, а налоговый номер и
название лежат атрибутами для нечёткой сверки с подтверждением человеком.

**Что это значит для Event OS:**
- **участники (люди)** адресуются — ID от телефона («АТС ID»), см. пункт 1;
- **контрагенты (ИП, ООО)** описываются: локальный ключ установки плюс признаки
  сверки (ИНН, название, телефон контакта), сверка — подсказка человеку, не
  автоматика;
- **карточка, которую раздаёт организатор**, приезжает с его опознаванием
  контрагента, и Light Plan привязывается к нему. Своего адреса организации не
  считает — поэтому двух властей над одной организацией не возникает. Это
  снимает вопрос, который иначе встал бы обязательно;
- организация **может стать участником** — но участником становится **человек**
  при ней, со своим ID; сама организация остаётся описанием.

**Остаётся открытым и относится к пункту 1:** перевыдача номера оператором.
Смена номера решена цепочкой прежних ID; перевыдача — другое: старый номер
через полгода достаётся постороннему, и карточка молча указывает на другого
человека. Алексей оценил вероятность как крайне малую для нашего масштаба и
отложил. Мессенджеры (WhatsApp, Signal) решают это переподтверждением и
предупреждением «ключ собеседника изменился» — когда появится головной сервер
ID, вопрос вернётся.

**Принцип хранения — поправка отложена намеренно, до самого сервера.**
Головной сервер обработки ID («просто список аккаунтов», Алексей) формулировке
«на нашем сервере не хранится ничего» противоречить не будет. Предлагалось
заточить её заранее — отклонено: сегодня утверждение **буквально верно**, ID
считается на устройстве и никуда не уходит, и буквально верный принцип работает
стеной, не требующей толкования. Менять подпись — в день запуска сервера, с
датой и причиной, а не авансом.

К тому дню держать наготове: различие **справочник против содержимого** (запись
«такой ID существует, вот куда стучаться» — маршрутизация; съёмки, клиенты,
кадры, документы — содержимое). Самое трудное место не сервер ID, а внутренний
мессенджер Event OS: сообщение в пути на сервере полежит обязательно, значит
переписке понадобится **своё** правило, а не расширительное толкование
«содержимого работы».

Разбор с примером и полным путём (включая три отвергнутых направления) — в
репозитории Light Plan, `DECISIONS.md`, разделы «Организация адреса не
получает: юрлицу нельзя ничего отправить» и «Принцип хранения заточен:
содержимое, а не "ничего"».

### 9. Студия в каталоге — площадка приходит из справочника, а не по приглашению
Идея Алексея, 30 августа 2026, ничего не начато. Номер сквозной: 7 и 8 заняты
пунктами в других разделах ниже.

**Дословно.** Есть база фотостудий (в будущем) и система бронирования для них
(BroniOS). Есть планировщик света, который умеет подсказывать свет (Light
Plan). Есть Event OS, которая умеет связывать наши PWA. Студия, добавляя себя в
каталог, показывает на карте, где находится, **в каком здании и на какой
стороне** — этим Light Plan становится вдвойне интереснее фотографам. Event OS
может добавлять студию как исполнителя, администраторы могут сообщать в Light
Plan информацию. Список оборудования становится осязаемым: у студии своя база
прокатного или дополнительного света. У фотографа появляется не просто
инструмент планирования, а инструмент связи со студией: продлить время в
студии, вызвать администратора, предсказать, где будет солнце на циклораме.

**Что здесь новое для Event OS.** Не роль — `22_Roles.md` §12.1 уже знает
`Venue Manager`, как знал Lead Photographer (пункт 8). Новое — **способ
попадания в проект**: участник приходит не по инвайту от организатора, а из
внешнего справочника, где он существовал до всякого проекта. Фаза 13 роадмапа
называет `shared contractors` и `contractor pools`, но со стороны агентства;
здесь то же самое со стороны самого подрядчика.

**Прямо задевает пункт 6 этого файла.** Там разбор закончился тем, что
организация адреса не получает вовсе: юрлицу нельзя ничего отправить,
дозываются человека при ней, а мировая практика (LEI, DUNS, налоговые номера)
опознаёт юрлица **назначением от держателя реестра**, а не вычислением. Каталог
студий — это и есть держатель реестра, которого в том разборе не существовало.
Вывод пункта 6 идея не отменяет (отправить по-прежнему можно только человеку),
но снимает его предпосылку: назначающая сторона появилась. Стояло не решено:
администратор отвечает своим ID человека, или студия получает собственный
назначенный адрес, а администратор — держатель ключа при нём.

**Решено (3 сентября 2026): студия получает собственный адрес — её
мобильный номер, тем же механизмом `appId(phone)`, что и у людей.**
Администратор своим личным ID для этой роли не отвечает; он — держатель
ключа при адресе студии.

Почему это не спорит с выводом пункта 6, хотя выглядит как «организация
всё-таки адресуется»: там запрет держался на том, что юрлицу нельзя ничего
отправить. У студии номер есть, по нему звонят, и человек при нём всегда
дежурит — отправляем по-прежнему человеку, просто у студии он есть всегда
(в отличие от контактного лица организации из примера с Анной — пункт 6 —
чей номер полисемичен сразу на несколько разных отношений).

Мобильный номер как основа, а не городской, — ничего нового не требует:
`appId` в Light Plan и так считается только с мобильного, и довод там
ровно этот же: городской номер принадлежит помещению и достаётся
следующему арендатору, мобильный переезжает вместе со студией.

**Уточнение по префиксам, тем же днём.** Первая формулировка предлагала
разные префиксы на тип площадки (`st…` для студии, `hall…` для банкетного
зала). Отклонено: тип площадки — рубрика, а не адрес. Light Plan уже
отказывался заводить тип места отдельным полем-списком (студия/банкетный
зал/лофт как значения выпадающего списка) — рубрика в адресе хуже, чем в
поле карточки: поле переименовывается, адрес — нет. Хуже того, префикс по
типу ломает воспроизводимость ID (тот самый провал, от которого уводил
пункт 6): один фотограф заведёт площадку студией, другой — банкетным
залом, и `st79…`/`hall79…` окажутся двумя разными узлами графа об одном и
том же месте, никогда не опознав друг друга.

Вместо этого — **один общий префикс на все площадки**, например `pl`:
`pl79618878078`. Тип остаётся атрибутом карточки, не частью адреса.
Гадать не о чем — площадка есть площадка, кто бы её ни заводил в каталог.

**Закрыто пунктом 3 (согласие) — РЕШЕНО (3 сентября 2026).** «Администраторы
сообщают в Light Plan информацию» — та же чужая рука в данных фотографа, что
и у организатора. Ответ один на оба случая (см. пункт 3 выше): администратор
может только предложить запись, она применяется лишь после подтверждения
фотографа. Два разных правила для одного действия не заводятся.

**Не покрывается 53_Notifications.md.** «Продлить время» — не уведомление, а
запрос с ответом и сроком: ответить нужно до конца оплаченного часа, молчание
означает «нет». Конвейер `Change → Affected Roles → … → Notification` описывает
доставку, но не переговорную пару «запрос — ответ» и не дедлайн ответа.

**Граница, которую стоит держать явно.** `90_Roadmap.md` §22 запрещает
`marketplace` в MVP — и это ограничение остаётся в силе. Каталог здесь означает
справочник плюс канал связи: ни сделки, ни комиссии, ни ранжирования студий.
Если граница начнёт стираться, запрет §22 применяется.

**Дополнение того же дня — уровни абстракции, и где Event OS не нужна.**
Алексей принёс разбор той же идеи другой моделью. Полезное для этого файла —
формулировка уровней: Event OS отвечает на «кто, с кем и когда», каталог
студий — на «где и как забронировать», Light Plan — на «как там будет свет».
Три системы знают разное об одной реальности и не дублируют друг друга; для
Event OS при этом безразлично, что один исполнитель фотограф, а другой
площадка, — это просто участники события.

**Но из этого не следует, что связь фотографа со студией идёт через Event
OS.** Обычная студийная съёмка — портрет, предметка, тест — это топология 1
(пункт 4): фотограф сам себе организатор, события в смысле Event OS нет
вовсе. Если продление часа и вызов администратора потребуют участия Event OS,
функция не заработает в самом частом случае. Event OS входит там, где студия —
исполнитель **события**: агентство ведёт свадьбу и держит площадку в том же
проекте. Значит каналов два, и они не подменяют друг друга: прямой
`фотограф ↔ студия` и `событие ↔ студия` через граф. Разводить их нужно
сознательно, а не выбирать один.

Разбор с русской стороны — Light Plan, `ROADMAP.md`, раздел «Студия в каталоге:
место, которое отвечает»; со стороны студии — `BroniOS/ROADMAP.md`, раздел
«Горизонт: студия в каталоге, фотограф на другом конце». Запись на английском

### 12. Событие — матрёшка: оболочка задаёт рамки, внутри подсущности — РЕШЕНО (18 сентября 2026)

**Откуда.** Багревью ленты дня в Light Plan: жест сдвигал съёмку на
таймлайне, а часы аренды студии и точки маршрута внутри неё оставались на
месте. Алексей: «Наш календарь вскрыл аспект, который мы не прописывали»; «это
мега уровень важности всей архитектуры … распространяется и на наши смежные
проекты».

**Решение (слова Алексея).** «События — это контейнеры-матрёшки. Внешняя
оболочка определяет рамки, внутри подсущности». «Двигать событие можно, но
пустое». «Упаковка не может двигать внутренности, внутренние события жёстко
привязаны к своему таймлайну, упаковка (внешний слой контейнера) не может быть
меньше внутреннего наполнения, но может быть больше». Почему в календаре
телефона этого правила нет: «внутри их события нет подсущностей, у нас же два
слоя». Для Event OS отдельно: «важно учесть, что события могут дробиться уже
внутри самого события». Уточнение того же дня: «точка без привязки к скелету
времени считается не привязанной. Точки на таймлайне — якорные» — оболочку
держат только подсущности со временем.

**Уже внесено:** `11_Graph_Model.md` — Design Rules, «Every event is a
container»; `13_Timeline_Canvas.md` — Design Rules, «The shell never moves its
contents». В Light Plan — `DECISIONS.md` («Событие — матрёшка») и
`docs/16_TIME_MODEL.md`; в BroniOS — `CLAUDE_CONTEXT.md` §38 и `ROADMAP.md`.

**Что решить при разборе.** Как правило ложится на Event → Scene: Scene ли
внутренний слой (моё предположение, не решение) и может ли Scene сама быть
оболочкой для более мелких сцен — «дробиться внутри события» говорит, что да,
глубина вложенности не оговаривалась. Что это значит для `54_Changes.md`:
перенос оболочки с содержимым запрещён, значит изменение времени непустого
события — это изменение его подсущностей по одной, а не одно изменение сверху.
Последнее — вывод из правила, Алексей его не формулировал.

### 10. Перевыдача номера оператором — РЕШЕНО (15 сентября 2026)

Продолжение пунктов 1 и 6, где это стоит «открытым». Открыто 14 сентября 2026,
стояло не решено: ниже находка и
варианты, выбирает Алексей вместе со стороной Event OS. Кодом в Light Plan не
закрыто.

**Симптом есть уже сегодня, без сервера.** Замер в Light Plan
(`tools/tmp/w7_measure.js`, пункт I, засев):
- номер клиентки Анны со съёмки 10 ноября 2025 года записан у нового клиента
  Петра в сентябре 2026-го. База номеров (`phoneIndex`) показывает их одной
  «связкой» — номер в двух карточках, наверху списка, ровно как «заказчик
  оказался отцом невесты»;
- Ольга сменила номер в декабре 2025-го, прежний лёг в `telLog` её карточки.
  Через девять месяцев с этим номером пришёл Игорь — связка «Ольга (прежний) ·
  Игорь».

Приложение не отличает «тот же человек в двух ролях» от «чужой человек с тем же
номером»: сравнивается ключ номера, и больше ничего.

**Где бьёт, по сторонам.**
- **Light Plan:** ложная связка в базе номеров. `appId` у нового держателя тот
  же (`id79131112233` у обоих). Матч со студией (`/booking/match`) шлёт только
  живые номера карточки, не `telLog`, и требует брони в той же студии в те же
  часы — ложное совпадение там практически невозможно.
- **BroniOS:** `recordPhotographerObserved` (`broni-auth/src/index.js`)
  ставит `photographerLP: true` на `appId` номера, и снимающего кода нет нигде —
  флаг переедет к новому держателю.
- **Event OS:** по пункту 1 ID адресует и ничего не авторизует, данные держит
  аккаунт. Значит перевыданный номер отдаёт постороннему **адрес** — приглашения
  и уведомления прежнего, — но не данные.

**Что приложение знает, чтобы судить.**
- ID выводится из номера (`appId`) и эпохи не имеет: номер 2025 года и тот же
  номер 2026-го дают одну строку.
- `me.ids` — цепочка прежних ID владельца с датой ухода (`at`). Про чужие номера
  такой цепочки нет.
- `telLog` карточки — ушедшие номера с именем, которое за ними стояло, и датой
  замены.
- Даты последнего контакта отдельным полем нет. Есть дата последней съёмки с
  этим номером (`phoneIndex`, `at`) и дата замены в `telLog`.
- Подтверждения номера нет ни у кого: свой номер владелец вписывает руками,
  клиентский вписывает фотограф.

**Варианты.**
1. **Оставить как есть** — решение 29 августа 2026: вероятность для масштаба
   крайне мала. Цена — ложная связка, которую видно глазами: в ней два разных
   имени.
2. **Давность на устройстве.** Номер, по которому контакта не было дольше N
   месяцев (последняя съёмка или дата в `telLog`), при новой встрече не
   склеивается молча: «этот номер был у Анны, 10 ноября 2025 — это тот же
   человек?». «Нет» — номер у прежней карточки помечается перевыданным, связки
   нет. Работает без сервера. N — вопрос: сроки, через которые операторы
   перевыдают номер, не проверены.
3. **Эпоха номера на сервере ID.** Смену держателя видит только тот, у кого
   держатель подтверждает номер, — сервер при заведении аккаунта Event OS.
   Новое подтверждение номера, уже бывшего за другим аккаунтом, закрывает
   прежнюю эпоху: ID остаётся строкой от номера, рядом едет дата подтверждения,
   и сторона со старой датой узнаёт «держатель номера сменился» — то, что
   мессенджеры показывают как «ключ собеседника изменился». Без головного
   сервера неисполнимо.
4. **2 и 3 вместе:** устройство подозревает по давности, сервер подтверждает
   эпохой, когда появится.

**Решить нужно на обеих сторонах сразу**, иначе один номер будет значить
разное в разных системах: что считается сменой держателя (давность? новое
подтверждение?) и кто объявляет её остальным. Пометит Light Plan номер
перевыданным, а BroniOS продолжит держать флаг на том же `appId` — и две
системы разойдутся на одном человеке.

Разбор с русской стороны — Light Plan, `DECISIONS.md`, раздел «Волна 7:
организации и мост в TOMCOH_OS».

**Решение: варианты 1 и 3.** До сервера — как есть, на обеих сторонах кода
нет. Когда заработает сервер ID — эпоха номера на нём. Давность на устройстве
(вариант 2), а с ним и вариант 4, не берутся.

Довод Алексея: «мы только в самом начале пути, на данном этапе мы только
начинаем рост, номер потеряется не скоро и наложение возникнет в перспективе,
когда у нас уже появится история и заработает сервер, вероятность такого
сценария крайне мала, номер должен попасть от одного пользователя нашей системы
к другому, это крайне маловероятно».

Что из этого следует:
- **До сервера.** Ложная связка в базе номеров Light Plan остаётся; цена
  варианта 1 — она видна глазами, в ней два разных имени. Флаг
  `photographerLP` в BroniOS по-прежнему не снимается нигде — это отдельная
  находка волны 7 Light Plan, решение её не трогает.
- **С сервером ID.** Сменой держателя считается новое подтверждение номера, уже
  бывшего за другим аккаунтом; оно закрывает прежнюю эпоху, рядом с ID едет
  дата подтверждения, сторона со старой датой узнаёт «держатель номера
  сменился». Как на смену эпохи отвечает флаг `photographerLP` — не решалось,
  вопрос времени сервера.

### 11. Полевой режим — работа без интернета — РЕШЕНО (16 сентября 2026)

Поставлено Алексеем 16 сентября 2026. Сценарий: выезд из города в горы, свет
от генераторов, роутеры везём с собой (3–6 штук на банкетный зал — «пустяки»),
рация у тех, кто может говорить, интернета нет весь съёмочный день.

**Что документы обещают сегодня и почему этого мало.** `10_Architecture.md`
(Offline Strategy), `14_Navigator.md §23`, `20_Workspaces.md §27`,
`40_UI_Philosophy.md §55` описывают офлайн одинаково: минимальный кэш для
чтения, «после восстановления соединения выполняется автоматическая
синхронизация». Это деградация на время разрыва. В поле разрыв — не
происшествие, а весь день, и люди в это время данные **создают**, а не
перечитывают. Обещанного режима в документах нет вовсе.

**Топология: хаб — точка встречи, а не сервер.** Первая мысль — «ноутбук
сервер, телефоны клиенты» — отклонена: она даёт единственную точку отказа
ровно там, где отказы вероятнее всего, и не решает исходную задачу, потому
что телефон, ушедший из зоны, снова офлайн — только уже относительно
локального сервера. Принято: **полный граф лежит на каждом устройстве,
каждое авторитетно для собственных записей.** Хаб нужен исключительно
потому, что браузер не умеет принимать входящие соединения, и два телефона
не могут поговорить напрямую. Его потеря стоит не данных, а возможности
обмениваться до следующей встречи.

Отсюда же снимается вопрос «разделилась комната — выбрали два хаба»: обе
стороны копят факты, при встрече журналы сливаются. Терять нечего — но
строго при условии, что журнал появился раньше выборов. Выборы без
сходящегося журнала теряют данные ровно в момент, когда связь
восстановилась.

**Телефонный mesh не берётся.** Довод Алексея: «ест батарею и сложнее
настроить, опыт работы с софтом для камер подсказывает, что это ненадёжно».
Инфраструктурный mesh между роутерами — другое дело и остаётся. Сеть привозят
с собой, а не находят на месте.

---

#### Что решается сейчас, на макетах: формат

Линия проходит не между дёшево и дорого, а между **форматом и
инфраструктурой**. Формат нельзя поменять, когда устройства уже в поле.

1. **Журнал первичен, состояние — его свёртка.** Сегодня наоборот:
   `app/core/graph.js` держит узлы напрямую (`nodes.set(id, after)`), а
   `Change` пишется побочно. Нужно перевернуть: слияние двух устройств
   становится объединением журналов и пересборкой, отдельного кода
   синхронизации не появляется вовсе.
2. **HLC вместо стенных часов.** `graph.js:208` выдаёт
   `chg_${Date.now()}_${rand}`. Без NTP часы расходятся, порядок записей
   становится неопределённым. Нужен `deviceId` плюс счётчик; календарное
   время остаётся человекочитаемой подписью, а не порядком.
3. **Терпимость к незнакомому.** Хостов много (Event OS, Light Plan,
   BroniOS, браузер с хаба), выпускаются они вразнобой, а журналы сливают в
   один. Неизвестные поля и неизвестные типы записей обязаны проходить
   насквозь **побайтово**. Устройство на старом бандле, выкинувшее
   непонятное поле и перезаписавшее запись, тихо испортит данные всем, и
   заметят это через неделю.
4. **Прописка в самой записи.** РФ/СНГ живёт на Яндексе (или VK — берётся
   тот, что даст больше), остальные на Cloudflare. Значит у события
   участники из двух домов, и граф живёт поперёк обоих. Дом записи
   решается в момент записи и едет вместе с ней.
5. **Происхождение записи.** Поле `source` в `_recordChange` уже есть.
   Добавляются `"Radio"` (решено голосом, внесено задним числом, с тем, кто
   передал и кто принял) и `"Calendar"`. Без этого граф расходится с
   реальностью, и наутро никто не знает, что из двух правда.

Правило разрешения конфликтов новым кодом не обрастает: у узла есть
владелец, для своих полей он выигрывает, чужая правка — не правка, а
`Pending Change` (`§3/§9`, уже реализовано). Сходиться консенсусом нужно
только там, где двое правят одно и то же чужое.

#### Что ждёт натива и настоящих серверов: инфраструктура

Провайдеры, домашний сервер, нативные оболочки, маяки BLE, протокол выборов
точки встречи, само железо хаба. Ни одно из этого не диктует формат, и ни
одно не блокируется макетами.

---

#### Клиенты: три хоста, одно ядро

```
Light Plan (натив)      — съёмочная команда
Event OS (натив)        — все остальные
браузер с хаба          — разовые роли и восстановление
```

Приложение ставят по признаку **чьим клиентом человек является**, а не по
роли в конкретном событии: роль меняется от проекта к проекту, продавец нет.
Разделение совпадает с уже существующей границей графа — ветка ассистентов
(`§2/§4`, `person-assistant` → `person-second-assistant`) не имеет ребра к
организатору и есть ровно съёмочная команда.

Ядро и ролевые лица — **веб-бандлы**, а не скомпилированный код. Правила
App Store (3.3.2) запрещают подгружать исполняемый код с явным исключением
для JavaScript в WebKit — на нём живут все гибриды. Без этого исключения два
натива означают два цикла релиза и разъехавшиеся версии ядра. С ним
обновление ядра не требует релиза ни в одном из приложений.

Побочно закрывается паритет: экран водителя в нативной оболочке и экран
водителя в браузере с хаба — одни и те же файлы. Разойтись им больше нечем.

#### Уведомления: push в поле невозможен

`53_Notifications.md §10` требует: Critical «всегда доставляется
push-уведомлением, независимо от общих настроек пользователя». Web Push идёт
через APNs, то есть через интернет. Без интернета мёртв не наш отправитель, а
постоянный сокет телефона к Apple — подменить его нечем, и имитация сервера
пушей стучалась бы в дверь, за которой никого нет. Пример из самого
документа — «Ceremony перенесена на 30 минут раньше» — это ровно полевой
случай.

Заменяется **локальным уведомлением**: нативное приложение получает запись от
хаба по локальному Wi-Fi и поднимает баннер само, без серверов. Пользователь
не отличает. Условие — приложение должно быть живо; отсюда маяк BLE на входе
как легальный способ разбудить выгруженное приложение (присутствие и
пробуждение — да, доставка сообщений — нет, веб-клиенту BLE недоступен).

`§17 Acknowledgement` тоже правится: пока Critical не подтверждена,
организатор видит открытый риск — в поле он увидит открытым риском весь день
и перестанет смотреть на индикатор к третьему часу.

**Канал доставки = роль × момент × связность.** Ведущий на сцене не может
говорить по рации (довод Алексея: «ведущему нельзя общаться по радио») и не
может печатать: ему нужен беззвучный текст, без вибрации — она слышна у
петлички, — и взгляд на две секунды. Фотограф в кадре примет вибрацию, но не
чтение. Водитель за рулём примет голос, но не текст. Одно и то же Critical —
четыре разные доставки.

Для ведущего это не уведомление, а **всегда включённое табло**:
`navigator.wakeLock` (Safari 16.4+), одна строка текущей инструкции, телефон
на клипсе у пюпитра. Пропущенный баннер хуже табло, которое всегда право.
Тяга вместо толчка.

И отдельно: **Critical не деградирует молча.** Если доставка физически
невозможна, организатор обязан увидеть это до отправки, а не после.

#### Чат

Чат нужен и работает в обоих режимах. Сообщения неизменяемы и только
дописываются — они никогда не конфликтуют, поэтому репликация чата дешевле
репликации графа. `24_Communication.md §30` уже описывает чат как поток
событий: **это тот же журнал, не второй механизм.** Отдельного «полевого
чата» не существует, меняется только то, с какими узлами идёт обмен.

Три вещи, которые в поле ломаются:

- `§61` перечисляет `SENT / DELIVERED / READ`, подразумевая сервер, который
  знает. При разрыве не знает никто. Нужны честные состояния — записано у
  меня / дошло до хаба / дошло до адресата. Галочка, которая врёт, хуже её
  отсутствия.
- **Сообщение, вставленное в прошлое.** При слиянии HLC может поставить
  запись выше уже прочитанных, и её не увидят никогда. Позиция по HLC, но
  новизна считается для каждого читателя отдельно, и шов виден: «написано
  18:40, пришло 19:15».
- **ACK — единственный ответ ведущего.** `§62` называет его полезнее
  «прочитано»; на сцене он не полезнее, а единственно возможный. Одно
  касание, реплицируется отдельной записью.

Вложения отделяются от сообщений: одно видео на 40 МБ не должно задерживать
канал, от которого зависят все.

#### Выезд как отдельная операция

Маршрут односторонний: город → горы. Всё, что не материализовано до выезда,
недоступно весь день. Значит нужна явная проверяемая операция с отчётом, а не
фоновая синхронизация «когда-нибудь дойдёт». Материализуются не узлы графа —
он маленький, — а **байты**: документы сцен, схемы зала, райдеры, тайлы карты
на последние километры, телефоны, сам клиент с живым сертификатом.

Отчёт двумерный, потому что «забыл поставить приложение» — городская
проблема, и ловить её надо в городе:

```
Содержимое  94%  — нет райдера, схемы зала, карты последних 12 км
Люди        6/8  — у Саши приложение не установлено
                   у Марины проект не выгружен (обмен 4 дня назад)
```

По жизненному циклу это граница `50_Event_Lifecycle.md §8 → §9`.

#### Восстановление без App Store

Удалил приложение, выгрузил из памяти, не поставил, пока был интернет — в
горах магазина нет. **Хаб раздаёт не только данные, но и сам клиент:**
подключился к Wi-Fi площадки, открыл адрес, получил работающее приложение.
Приложение едет в кофре наравне с роутерами.

Адрес человек узнаёт физически: captive portal на роутере (iOS сам открывает
шторку «войти в сеть») и ламинированный QR на кофре и колл-листе. Это ровно
«механическая ссылка» из `§5` — передача не требует сервера в момент самой
передачи.

Личность возвращается сама: `appId()` — чистая функция от номера
(`app/core/id.js`), тот же номер даёт тот же ID, ни почты, ни пароля, ни
сервера. Дыра известна и принимается: ввести чужой номер может кто угодно, а
проверить в поле нечем. Поэтому возврат в проект — `Pending Change`,
подтверждаемый организатором со своего устройства. Привратник в поле — живой
человек в пятидесяти метрах.

Из этого следует требование к вебу: он обслуживает разовые роли (водитель,
курьер, декоратор, официант, повар — официант не поставит приложение ради
одного вечера) **постоянно**, а не как запасной вариант. Отстать ему нельзя.

Обмен должен идти непрерывно и жадно — не ради свежести, а чтобы удаление
приложения стоило минут, а не съёмочного дня: потолок потери задаёт то, что
успело дойти до хаба.

#### Календарь — витрина, а не источник

Календарь сидит на Google ради корректной интеграции в календари iOS, и
поэтому работает только по интернету. Значит время сцены, живущее **только**
в календаре, в поле не существует. Календарь — проекция наружу; правка,
сделанная в нём, возвращается как `Pending Change` с `source: "Calendar"`, а
не как истина.

---

**Решение.** Полевой режим принимается как нижняя ступень уже существующей
лестницы, а не как отдельная экзотика для экспедиций. Ось у всех трёх
ступеней одна — достижимость, а не отказ оборудования:

```
город, РФ          до Cloudflare не всегда доходит  →  второй провайдер
площадка в горах   не доходит ни до кого            →  хаб в кофре
зал на банкете     хаб за стеной                    →  роутеры
```

Поэтому журнал — не полевая функция. Он же обслуживает двухрегиональную
схему (участники события лежат в двух домах данных) и делает центральный
сервер необязательным **в момент использования**. Резервирование провайдеров
закрывает падение провайдера; оно не закрывает неудачный деплой
(реплицируется на оба), блокировку по юрисдикции и последнюю милю.

Побочно закрывается место, названное в `§6` самым трудным: «сообщение в пути
на сервере полежит обязательно, значит переписке понадобится своё правило».
В поле оно лежит на хабе в кофре и до центрального сервера не доходит вовсе.
Правило для города всё равно нужно, но у него появляется структурное
исключение, а не оговорка.

**Что этим не решается и остаётся открытым.**
- Порог `N` роутеров, схема моста и кто держит DHCP — инфраструктура, не
  формат. Правило одно и известно: один L2-сегмент, один SSID, ровно один
  DHCP, иначе mDNS умирает на границе роутера и хаб не виден с дальней точки.
- Сертификат для secure context (Service Worker и установка PWA требуют его,
  `http://192.168.x.x` не подходит) — городская задача из чек-листа выезда,
  с датой обновления в календаре.
- Протокол выборов точки встречи не проектировался. Порядок предпочтения —
  коробка в кофре, затем любой Mac в сети, затем телефон с открытым
  приложением; последнее требует натива и работает только пока приложение на
  экране, фонового демона на iOS не будет.
- Правило переписки для города (`§6`) остаётся за Event OS.
- Что именно материализуется в «выезд» по типам объектов — отдельная работа
  по `25_Documents.md` и `13_Timeline_Canvas.md`.

целиком), `53_Notifications.md §10, §14–15, §17` (push не единственный канал
Critical; канал зависит от роли, момента и связности), `24_Communication.md
§61–62` (состояния доставки при разрыве, ACK как ответ), `50_Event_Lifecycle.md
§8–9` (выезд как переход), `14_Navigator.md §23`, `20_Workspaces.md §27`,
`40_UI_Philosophy.md §55–56`.
