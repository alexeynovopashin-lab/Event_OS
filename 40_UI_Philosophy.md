# UI Philosophy

**Document:** `40_UI_Philosophy.md`  
**Version:** `0.1.0`  
**Status:** Draft

---

## 1. Назначение

Этот документ определяет философию интерфейса системы.

UI не должен быть визуальным отражением внутренней архитектуры.

Внутри системы может существовать сложный граф:

```text
Projects
Clients
Teams
Roles
Tasks
Documents
Timeline
Finance
Communication
Postproduction
Permissions
Dependencies
Events
````

Пользователь не должен видеть эту сложность целиком.

Главная задача интерфейса:

> **Показать человеку именно ту информацию, которая нужна ему сейчас для принятия следующего действия.**

---

# 2. Главная метафора — навигатор

Система должна работать как хороший автомобильный навигатор.

Навигатор знает:

* весь маршрут;
* все дороги;
* пробки;
* перекрытия;
* альтернативные маршруты;
* конечную точку;
* текущую позицию.

Но водитель не видит одновременно всю карту в виде инструкции:

```text
через 2 км повернуть направо
через 3.4 км перестроиться
через 5 км будет мост
через 7 км заправка
через 12 км ресторан
```

Он получает:

```text
Через 150 м — направо.
```

После поворота:

```text
Продолжайте прямо.
```

Если возникло изменение:

```text
Впереди пробка.
Маршрут изменён.
```

Именно так должна работать система.

---

# 3. Система знает больше пользователя

Это фундаментальный принцип.

```text
System Knowledge
        ↓
Context Engine
        ↓
Role
        ↓
Current Position
        ↓
Relevant Information
        ↓
User
```

Пользователь не обязан знать модель системы.

Он не должен знать:

* какие графы существуют;
* какие сущности связаны;
* какие автоматические правила сработали;
* какие зависимости находятся за пределами его зоны ответственности.

---

# 4. Не показывать базу данных

Плохой интерфейс:

```text
Projects
Tasks
Contacts
Documents
Messages
Budget
Calendar
Files
Contractors
Statuses
```

Это интерфейс базы данных.

Хороший интерфейс:

```text
Что сейчас происходит?
Что мне нужно сделать?
Что изменилось?
Что произойдёт дальше?
```

---

# 5. UI как слой контекста

Архитектура:

```text
Graph
  ↓
Context Engine
  ↓
Navigator
  ↓
UI
```

UI не должен самостоятельно решать:

> «Что сейчас важно?»

Это задача Context Engine.

UI должен хорошо представить уже выбранный контекст.

---

# 6. Три уровня информации

Интерфейс должен работать минимум на трёх уровнях.

## Level 1 — Now

Что происходит сейчас?

```text
Сейчас:
Съёмка в ресторане

Следующее:
Переезд через 25 минут
```

---

## Level 2 — Next

Что будет следующим?

```text
Следующее:
ЗАГС

После:
Прогулка

Затем:
Банкет
```

---

## Level 3 — Full Context

Полная информация доступна по запросу.

```text
Project
Timeline
Documents
People
Finance
Communication
Postproduction
```

Она не должна находиться на первом экране постоянно.

---

# 7. Принцип progressive disclosure

Информация раскрывается постепенно:

```text
Summary
 ↓
Context
 ↓
Details
 ↓
Full Data
```

Пользователь получает подробности только тогда, когда они ему понадобились.

---

# 8. Информация должна быть порционной

Не:

```text
100 событий
37 задач
18 документов
12 подрядчиков
8 чатов
```

А:

```text
Сейчас:
Выезд через 15 минут.
```

После выполнения:

```text
Следующее:
Церемония через 42 минуты.
```

---

# 9. Главный объект интерфейса — ситуация

UI должен быть построен не вокруг сущности, а вокруг ситуации.

Не:

```text
Photographer
```

а:

```text
Фотограф сейчас едет на прогулку.
```

Не:

```text
Weather
```

а:

```text
Через час дождь.
Зонтики уже добавлены в маршрут.
```

Не:

```text
Task
```

а:

```text
Ретушёр закончил.
Нужно проверить фотографии.
```

---

# 10. Timeline — основной инструмент

Timeline является центральным визуальным инструментом системы.

Пример:

```text
START
  │
  ├── Preparation
  │
  ├── Ceremony
  │
  ├── Transfer
  │
  ├── Walk
  │
  ├── Golden Hour
  │
  ├── Reception
  │
  └── END
```

Timeline показывает проект во времени.

---

# 11. Timeline не должен быть одинаковым для всех

У одного проекта существует один Timeline.

Но пользователь получает его представление согласно своей роли.

```text
Project Timeline
       ↓
Role
       ↓
Relevant Timeline
```

---

# 12. Пример

Фотограф:

```text
10:00 Preparation
11:30 Transfer
12:00 Ceremony
13:00 Portraits
14:30 Reception
18:40 Golden Hour
```

Ведущий:

```text
17:30 Sound Check
18:00 Guests Arrival
18:30 Reception
19:00 Opening
20:00 First Dance
```

Водитель:

```text
11:30 Pickup
12:00 Ceremony
13:00 Transfer
14:00 Hotel
```

Ведущему не нужен весь маршрут фотографа.

---

# 13. Timeline как слой над графом

Timeline не является самостоятельной системой.

Он представляет временную проекцию графа.

```text
Graph
  ↓
Temporal Projection
  ↓
Timeline
```

---

# 14. Контекст важнее времени

Timeline отвечает:

> Когда?

Context Engine отвечает:

> Что именно мне нужно знать об этом моменте?

Например:

```text
14:00
Transfer
```

Для водителя:

```text
Кого забрать:
Bride + Groom

Куда:
Restaurant

Автомобиль:
Mercedes

Контакт:
Organizer
```

Для фотографа:

```text
Съёмка:
Portraits

Свет:
Golden Hour через 35 мин

Локация:
Park

Важно:
Не задерживаться
```

Одна точка времени.

Разный контекст.

---

# 15. Current Position

Каждый пользователь имеет условную текущую позицию в проекте.

```text
Project Timeline
       ↓
Current Position
       ↓
Relevant Context
```

Current Position может определяться:

* временем;
* завершёнными действиями;
* геолокацией;
* статусом;
* ролью;
* событиями;
* вручную.

---

# 16. Current Context

На экране должно быть понятно:

```text
Где я?
Что происходит?
Что дальше?
```

Минимальная модель:

```text
NOW
NEXT
ALERT
```

---

# 17. NOW

Основной блок:

```text
Сейчас

Портретная съёмка
Park
14:00–15:00
```

---

# 18. NEXT

Следующий важный шаг:

```text
Далее

Переезд в ресторан
15:00
≈ 20 минут
```

---

# 19. ALERT

Только значимые отклонения:

```text
⚠ Дождь через 20 минут.

Маршрут прогулки изменён.
```

или:

```text
⚠ Ретушёр запросил уточнение.
```

---

# 20. Не превращать UI в ленту уведомлений

Система не должна сообщать:

```text
Иван открыл документ.
Мария изменила задачу.
Пётр написал сообщение.
Файл синхронизирован.
```

если это не требует действия пользователя.

---

# 21. Notification ≠ Event

Событие:

```text
Retoucher started job.
```

не обязательно является уведомлением.

Уведомление:

```text
Retoucher finished.
You need to review the result.
```

является действием.

---

# 22. Action over information

Предпочтение:

```text
Нужно подтвердить макет.
[Открыть]
```

вместо:

```text
Макет был изменён пользователем Ивановым в 14:32.
```

---

# 23. Исключения важнее нормы

Если всё идёт по плану:

```text
✓ Всё по плану
```

не нужно объяснять пользователю весь процесс.

Если произошло отклонение:

```text
⚠ Машина задерживается на 20 минут.
```

система должна показать:

```text
Что произошло?
Что изменилось?
Что делать?
```

---

# 24. UI должен быть спокойным

Интерфейс не должен постоянно кричать:

```text
NEW
URGENT
IMPORTANT
WARNING
ACTION
```

Если всё важно, ничего не важно.

---

# 25. Визуальная иерархия

Основной порядок:

```text
1. Где я
2. Что сейчас
3. Что дальше
4. Что изменилось
5. Что можно сделать
6. Подробности
```

---

# 26. Карточка

Карточка — основной контейнер информации.

Она должна отвечать на вопрос:

> Что это?

и:

> Что мне с этим делать?

---

# 27. Карточка проекта

Минимальная карточка:

```text
Иванов + Петрова
24 августа

10:00–22:00

◉ Wedding
☀ 24°C

Фотография
● Подготовка
```

Подробности раскрываются по запросу.

---

# 28. Не перегружать карточки

Плохая карточка:

```text
Project
Client
Budget
Tasks
Weather
Documents
Contractors
Messages
Payments
Timeline
Files
```

Хорошая:

```text
Название
Дата
Главный статус
Следующее действие
```

---

# 29. Details on demand

Подробности открываются:

```text
Card
 ↓
Tap / Click
 ↓
Detail View
```

Не нужно помещать весь объект на карточку.

---

# 30. Один экран — одна задача

Экран не должен одновременно пытаться быть:

* календарём;
* CRM;
* чатом;
* бухгалтерией;
* файловым менеджером;
* таск-менеджером.

Если пользователю нужно выполнить действие, интерфейс должен убрать второстепенные элементы.

---

# 31. Не строить универсальный Dashboard

Универсальный dashboard:

```text
Weather
Calendar
Tasks
Messages
Budget
Projects
People
Files
```

обычно превращается в панель управления базой данных.

Вместо него:

```text
Today
Now
Next
Exceptions
```

---

# 32. Главный экран зависит от роли

Организатор:

```text
Projects
Today
Exceptions
Timeline
```

Фотограф:

```text
Now
Next
Shooting
Postproduction
Client
```

Ретушёр:

```text
My Jobs
Due Today
Review
```

Ведущий:

```text
Today's Event
Next Action
Schedule
```

Молодожёны:

```text
Preparation Status
Next Milestone
Messages
```

---

# 33. Роль ≠ отдельное приложение

Все используют одну систему.

Различается:

```text
Context
Permissions
Navigation
Default Views
```

---

# 34. Permissions не должны определять UX целиком

Permission отвечает:

> Можно ли это видеть или делать?

Context отвечает:

> Нужно ли это показывать сейчас?

Это разные вещи.

---

# 35. Chat

У всех пользователей может быть чат.

Но чат не должен быть главным способом управления проектом.

Плохо:

```text
«Фотограф, маршрут поменялся»
```

Хорошо:

```text
Timeline
 ↓
Route Changed
 ↓
Affected Users
```

и только после этого:

```text
Chat
```

может использоваться для обсуждения.

---

# 36. Chat как контекст

Сообщение должно иметь возможность быть связано с:

```text
Project
Timeline Event
Task
Document
Job
Client
```

---

# 37. Не заставлять искать информацию в чате

Информация, важная для работы, должна становиться структурированным объектом.

Например:

```text
«Давайте перенесём фотосессию на 16:00»
```

после подтверждения:

```text
Timeline Event
16:00
Portrait Session
```

---

# 38. Chat не является Source of Truth

Source of Truth:

```text
Timeline
Project State
Documents
Jobs
Finance
```

Chat является коммуникацией вокруг этих объектов.

---

# 39. Изменения должны распространяться

Если изменилось:

```text
Timeline Event
```

система должна определить:

```text
Affected Users
Affected Jobs
Affected Documents
Affected Deadlines
```

и показать изменения только тем, кого они касаются.

---

# 40. Принцип «сесть в кино с середины»

Исполнитель может быть подключён:

```text
за 1 год
за месяц
за неделю
за день
за час
```

Он не должен читать всю историю проекта.

При подключении система должна создать:

```text
Context Brief
```

---

# 41. Context Brief

Например для фотографа:

```text
Свадьба Иванов + Петрова
24 августа

Вы:
Фотограф

Ваша задача:
Съёмка 10:00–22:00

Важно:
Церемония перенесена на 13:30.

Следующее:
10:00 — сборы

Контакт:
Организатор Анна

Последнее изменение:
Вчера маршрут прогулки изменён.
```

---

# 42. «Что изменилось?»

Новый пользователь должен видеть не всю историю проекта, а:

```text
Изменения с момента вашего подключения
```

---

# 43. Context Delta

Пример:

```text
Изменилось:

13:00 → 13:30
Церемония перенесена.

Локация прогулки:
Park → Botanical Garden
```

---

# 44. Onboarding исполнителя

Однодневный исполнитель не должен проходить длинное обучение.

Минимум:

```text
Who am I?
What is this project?
What is my role?
What do I do now?
What happens next?
Who do I contact?
```

---

# 45. One-Day User

Для временного исполнителя:

```text
Temporary Access
 ↓
Context Brief
 ↓
Current Task
 ↓
Chat
 ↓
Completion
 ↓
Access Expiration
```

---

# 46. Мобильный интерфейс

Mobile предназначен прежде всего для:

```text
Now
Next
Navigation
Communication
Notifications
Quick Actions
```

---

# 47. Desktop интерфейс

Desktop предназначен прежде всего для:

```text
Planning
Management
Timeline
Documents
Large Data
Multiple Projects
Postproduction
Finance
```

---

# 48. PWA

PWA является основным способом доставки интерфейса.

```text
Web
 ↓
PWA
 ├── Desktop
 ├── iOS
 └── Android
```

---

# 49. Mobile ≠ уменьшенный Desktop

Нельзя просто уменьшить desktop-интерфейс.

Mobile должен менять приоритеты.

Desktop:

```text
Timeline + Details + Side Panel
```

Mobile:

```text
Current Event
 ↓
Next
 ↓
Action
```

---

# 50. Desktop ≠ увеличенный Mobile

На большом экране можно одновременно показать:

```text
Timeline
Project
People
Changes
Documents
```

но без потери иерархии.

---

# 51. Responsive Layout

Основные breakpoint'ы должны определяться не устройствами, а плотностью информации.

```text
Compact
Medium
Expanded
```

---

# 52. Touch

На мобильном:

* крупные touch targets;
* минимум точных действий;
* swipe там, где он естественен;
* важные действия доступны одной рукой.

---

# 53. Keyboard / Mouse

На desktop:

* keyboard shortcuts;
* hover information;
* drag & drop;
* multi-selection;
* context menus;
* быстрые действия.

---

# 54. Интерфейс должен быть быстрым

Система используется во время реального события.

Задержка в интерфейсе особенно критична:

```text
в машине
на площадке
во время съёмки
на банкете
при смене маршрута
```

---

# 55. Offline / Unreliable Network

Система должна учитывать нестабильный интернет.

Особенно для:

```text
Timeline
Contacts
Current Context
Documents
Recent Updates
```

Минимальный необходимый контекст должен быть доступен локально.

---

# 56. Sync

При восстановлении соединения:

```text
Local State
 ↓
Sync
 ↓
Conflict Resolution
 ↓
Current State
```

---

# 57. Конфликты

Если два пользователя одновременно изменили данные:

```text
User A
 ↓
Timeline 14:00

User B
 ↓
Timeline 14:30
```

система не должна молча перезаписывать данные.

Должно быть понятно:

```text
Conflict detected
```

---

# 58. Дизайн-система

UI должен иметь небольшое количество базовых компонентов:

```text
Card
Timeline
Status
Chip
Button
Input
List
Sheet
Dialog
Toast
Banner
Avatar
Progress
```

---

# 59. Компоненты должны быть семантическими

Например:

```text
<Status>
```

а не:

```text
<GreenCircle>
```

UI должен описывать смысл, а не внешний вид.

---

# 60. Цвет

Цвет используется для:

```text
Status
Priority
Warning
Brand
```

а не для декоративного заполнения интерфейса.

---

# 61. Цвет не должен быть единственным способом передачи состояния

Например:

```text
● Ready
```

а не только:

```text
зелёная точка
```

Это важно для доступности.

---

# 62. Типографика

Типографика должна создавать иерархию:

```text
Primary
Secondary
Meta
```

Не нужно использовать много размеров и начертаний.

---

# 63. Числа

Числа должны быть визуально легко считываемыми:

```text
10:00
24 AUG
25 000 ₽
14:30
```

Особенно:

* время;
* даты;
* суммы;
* расстояния;
* длительности.

---

# 64. Пространство

Whitespace используется для группировки информации.

Пустое место не является потерянным пространством.

---

# 65. Не бояться пустоты

Интерфейс организатора не должен выглядеть как:

```text
CRM
+
ERP
+
Messenger
+
Calendar
+
Accounting
```

Он должен выглядеть как спокойный инструмент управления сложной ситуацией.

---

# 66. Карточки должны быть визуально различимы

Но не превращаться в коллекцию разноцветных блоков.

Различие может строиться через:

```text
Typography
Spacing
Iconography
Hierarchy
Status
```

---

# 67. Иконки

Иконка должна:

1. быть понятной;
2. работать на малом размере;
3. иметь устойчивый силуэт;
4. не требовать расшифровки.

Не использовать иконку только ради украшения.

---

# 68. Текст важнее иконки

Если значение не очевидно:

```text
Иконка + текст
```

лучше:

```text
Иконка без текста
```

---

# 69. Empty States

Пустой экран должен отвечать:

```text
Почему здесь пусто?
Что это означает?
Нужно ли что-то делать?
```

Например:

```text
Нет активных задач.

Всё выполнено.
```

а не:

```text
No data.
```

---

# 70. Loading

Система должна показывать состояние загрузки, соответствующее структуре контента.

Не использовать бесконечный spinner там, где можно показать skeleton.

---

# 71. Errors

Ошибка должна объяснять:

```text
Что произошло?
Можно ли продолжить?
Что делать?
```

Плохо:

```text
Error 500
```

Хорошо:

```text
Не удалось загрузить маршрут.

Попробовать снова
```

---

# 72. Destructive Actions

Удаление и другие необратимые действия должны быть:

```text
Явными
Понятными
Подтверждаемыми
```

---

# 73. Undo

Если действие можно безопасно отменить:

```text
Deleted
[Undo]
```

лучше сложного confirmation dialog.

---

# 74. Не использовать модальные окна без необходимости

Модальное окно прерывает контекст.

Предпочтение:

```text
Inline
Sheet
Side Panel
Detail View
```

---

# 75. Detail View

Detail View является естественным способом перехода:

```text
Summary
 ↓
Details
```

Например:

```text
Wedding Card
 ↓
Wedding Detail
```

---

# 76. Side Panel на Desktop

На desktop детали можно открывать рядом с основным контекстом:

```text
Timeline
│
├── Event
│
└── Detail Panel
```

Пользователь не теряет позицию.

---

# 77. Bottom Sheet на Mobile

На мобильном аналогичная модель:

```text
Current Context
 ↓
Bottom Sheet
```

---

# 78. Navigation

Основная навигация должна быть ограниченной.

Не нужно создавать 15 пунктов меню.

Пример:

```text
Today
Projects
Messages
More
```

Внутри Project:

```text
Overview
Timeline
People
Documents
Finance
```

---

# 79. Navigation ≠ Architecture

Количество разделов интерфейса не обязано соответствовать количеству сущностей в backend.

```text
100 entities
```

могут быть представлены:

```text
5 navigation areas
```

---

# 80. Search

Search нужен для случаев, когда пользователь знает, что ищет.

Например:

```text
Иванов
Договор
Фотограф
25 августа
```

Search не должен заменять нормальную навигацию.

---

# 81. Global Search

Global Search может искать:

```text
Projects
People
Documents
Messages
Jobs
Events
```

с учётом permissions.

---

# 82. Command Palette

На desktop может существовать:

```text
⌘K
```

для быстрых действий:

```text
Open project
Create event
Find person
Send message
Jump to date
```

Это ускоряет работу профессиональных пользователей.

---

# 83. Contextual Actions

Действия должны находиться рядом с объектом.

Например:

```text
Retouch Job
[Review]
```

а не:

```text
Menu
→ Jobs
→ Retouch
→ Find Job
→ Review
```

---

# 84. Один главный Action

В большинстве контекстов должен быть один очевидный primary action.

Например:

```text
[Подтвердить маршрут]
```

а второстепенные действия:

```text
Изменить
Поделиться
Подробнее
```

---

# 85. Не заставлять пользователя думать о системе

Плохой вопрос:

> В какой раздел мне зайти?

Хороший интерфейс отвечает:

> Вот что тебе сейчас нужно сделать.

---

# 86. Система должна уменьшать когнитивную нагрузку

Организатор одновременно удерживает:

```text
десятки клиентов
сотни подрядчиков
сроки
локации
маршруты
бюджеты
документы
изменения
```

Система должна забирать эту нагрузку на себя.

---

# 87. Система как внешняя память

Главная функция UI:

> **Не заставлять человека помнить то, что система может помнить сама.**

Например:

```text
Организатор знает:
«Мы это вроде обсуждали».

Система знает:
Когда.
Где.
С кем.
Что решили.
Что изменилось.
Кого это касается.
```

---

# 88. Не превращать пользователя в оператора CRM

Пользователь не должен постоянно:

```text
обновлять статусы
переносить задачи
пересылать сообщения
дублировать информацию
напоминать подрядчикам
```

если система может связать эти действия автоматически.

---

# 89. Автоматизация без магии

Автоматическое действие должно быть:

```text
Предсказуемым
Объяснимым
Отменяемым
```

---

# 90. AI

AI является дополнительным слоем.

```text
Core System
       ↓
Context
       ↓
Navigator
       ↓
Optional AI
```

Без AI система должна работать полностью.

---

# 91. AI не должен владеть интерфейсом

Не строить продукт как:

```text
Chat with AI
```

AI может быть помощником внутри интерфейса:

```text
Система
+
структурированные данные
+
Navigator
+
AI
```

---

# 92. AI как объяснитель

Например:

```text
Почему изменился маршрут?
```

AI может ответить:

```text
Из-за дождя прогулка перенесена на локацию B.
Фотограф, водитель и координатор уведомлены.
```

Но источник истины:

```text
Timeline + Events
```

---

# 93. AI как фильтр

Пользователь может спросить:

```text
Что изменилось по свадьбе Ивановых за последние два дня?
```

AI собирает ответ из структурированных данных.

---

# 94. Accessibility

Система должна учитывать:

* достаточный размер текста;
* контраст;
* клавиатурную навигацию;
* screen readers;
* отсутствие зависимости от цвета;
* touch targets;
* понятные labels.

---

# 95. Internationalization

Архитектура UI должна позволять:

```text
Language
Currency
Date Format
Time Format
Number Format
Timezone
```

без изменения логики приложения.

---

# 96. Timezone

Event всегда должен иметь timezone.

Особенно важно для:

```text
Travel
Remote Teams
Agencies
Multiple Cities
```

---

# 97. Localization

Не следует хранить локализованный текст внутри бизнес-логики.

UI:

```text
Translation Key
```

Data:

```text
Semantic Value
```

---

# 98. Visual Identity

Каждая организация может иметь минимальную айдентику:

```text
Logo
Primary Color
Secondary Color
```

Этого достаточно.

---

# 99. White Label

Организация не должна перестраивать интерфейс.

Она только задаёт:

```text
Logo
Colors
Name
```

Основная система остаётся единой.

---

# 100. Не делать «корпоративные порталы»

White Label не должен превращать систему в:

```text
Корпоративный портал
```

Главная UX-модель остаётся общей.

---

# 101. Visual Language

Общий стиль должен быть:

```text
Calm
Clear
Precise
Light
Functional
Human
```

Избегать:

```text
Dashboard aesthetic
Excessive gradients
Excessive shadows
Visual noise
Gamification
```

---

# 102. Система должна ощущаться как инструмент

Не:

```text
социальная сеть
```

не:

```text
CRM для отдела продаж
```

не:

```text
таск-менеджер
```

а:

> **рабочий инструмент организатора и его команды.**

---

# 103. Главный UX-принцип

```text
Система знает весь проект.
Пользователь знает свою работу.
```

---

                    PROJECT GRAPH

# 105. Короткая формула

> **Не показывать пользователю систему. Показывать ему ситуацию.**

И ещё короче:

```text
Know everything.
Show little.
Show the right thing.
Show it at the right time.
```

---

# 106. UX North Star

Любой новый экран, компонент или функция должны пройти четыре вопроса:

1. **Кто это сейчас смотрит?**
2. **Где он находится в процессе?**
3. **Что ему нужно знать прямо сейчас?**
4. **Какое следующее действие он должен совершить?**

Если интерфейс не может ответить на эти вопросы, он, вероятно, показывает слишком много информации.

Главная цель UI:

> **Превратить сложный граф проекта в простой следующий шаг для конкретного человека.**
