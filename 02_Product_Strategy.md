# Purpose

Определить стратегию развития Event OS как продукта.

Документ отвечает на вопросы:

- Какую проблему мы решаем?
- Для кого создается платформа?
- Почему существующие решения недостаточны?
- Каким образом будет расти продукт?

---

# Product Definition

Event OS — это контекстно-ориентированная операционная система для event-индустрии.

Основной продукт — не CRM.

Основной продукт — единая среда взаимодействия всех участников мероприятия.

---

# Core Value

Мы продаем не функции.

Мы продаем спокойствие.

Пользователь должен быть уверен, что:

- он ничего не забыл;
- изменения не потеряются;
- нужные люди получили актуальную информацию;
- проект развивается по плану.

Главная ценность продукта — снижение когнитивной нагрузки.

---

Организаторы мероприятий.

Именно организатор является владельцем проекта и создает пространство для совместной работы.

---

## Secondary

Подрядчики.

- фотографы;
- видеографы;
- ведущие;
- координаторы;
- декораторы;
- флористы;
- диджеи;
- музыканты;
- рестораны;
- кейтеринг;
- кондитеры;
- стилисты;

Они получают ограниченный доступ исключительно к своему мероприятию.

После завершения проекта доступ автоматически архивируется.

---

# Product Positioning

Мы не конкурируем напрямую с:

- CRM;
- Task Manager;
- Messenger;
- Calendar;
- ERP.

Мы объединяем их вокруг одного события.

---

# Event-First Strategy

Любая новая функция должна отвечать на вопрос:

> Делает ли она событие более управляемым?

Если ответ отрицательный — функция не входит в продукт.

---

# Context-First Strategy

Мы не увеличиваем количество информации.

Мы увеличиваем качество информации.

Каждый экран должен отвечать только на один вопрос:

> Что сейчас важно именно мне?

---

# Timeline-First Strategy

Timeline является главным интерфейсом продукта.

Все действия начинаются из Timeline.

Все изменения отображаются через Timeline.

Все объекты имеют собственную позицию во времени.

---

# Mobile First

Телефон является главным рабочим устройством мероприятия.

Во время события пользователь редко открывает ноутбук.

Основная работа происходит с мобильного устройства.

Интерфейс должен быть рассчитан на использование одной рукой.

---

# Desktop First For Management

Подготовка мероприятия требует большого экрана.

Компьютер используется для:

- подготовки проекта;
- работы с документами;
- построения структуры мероприятия;
- управления командами;
- аналитики;
- работы с большим количеством информации.

Desktop не является увеличенной копией мобильного приложения.

Он предоставляет другой уровень управления.

---

# PWA First

Основной клиент платформы — Progressive Web App.

Причины:

- единая кодовая база;
- iOS;
- Android;
- Windows;
- macOS;
- Linux;
- быстрое обновление;
- минимальная стоимость поддержки.

Нативные приложения являются дополнительным уровнем, а не обязательным компонентом.

---

# Modular Architecture

Каждый пользователь использует только необходимые ему возможности.

Например:

Фотографу не нужна бухгалтерия.

Ведущему не нужен постпродакшен.

Ресторану не нужны маршруты фотографа.

Платформа должна автоматически адаптироваться под пользователя.

---

# AI Optional

ИИ никогда не является обязательным.

Платформа должна полноценно работать без искусственного интеллекта.

ИИ усиливает существующие процессы:

- анализ;
- рекомендации;
- поиск информации;
- генерация документов;
- контроль рисков.

---

# Finance Philosophy

Event OS не является банковской системой.

Мы не принимаем платежи.

Мы не предоставляем эквайринг.

Мы не заменяем бухгалтерию.

Платформа хранит только статус финансовых обязательств.

Например:

- Не выставлено.
- Выставлен счет.
- Частично оплачено.
- Оплачено.
- Возврат.
- Закрыто.

При необходимости пользователь самостоятельно использует привычную бухгалтерскую систему.

---

# Communication Philosophy

Вся коммуникация относится к конкретному событию.

Не существует "общего чата".

Каждая сцена мероприятия может иметь собственную переписку.

Каждый объект может содержать обсуждение.

Пользователь никогда не ищет информацию среди сотен сообщений.

Он открывает нужный объект и сразу видит связанную коммуникацию.

---

# Collaboration

Платформа должна поддерживать совместную работу:

- организаторов;
- агентств;
- подрядчиков;
- фрилансеров;
- временных сотрудников.

Один пользователь может одновременно участвовать в нескольких организациях.

Один подрядчик может работать сразу с несколькими агентствами.

---

---

# Network Effect

Каждый новый зарегистрированный исполнитель увеличивает ценность платформы.

Организатору проще пригласить специалиста, уже использующего Event OS.

Исполнителю проще работать с агентствами, использующими Event OS.

Со временем формируется профессиональная сеть отрасли.

---

# Marketplace Without Marketplace

Event OS не стремится стать биржей исполнителей.

Платформа помогает существующим профессиональным связям работать эффективнее.

Поиск новых подрядчиков может появиться позднее как дополнительная возможность, но не является целью продукта.

---

# Success Metrics

Ключевые показатели продукта:

- уменьшение количества сообщений;
- уменьшение количества телефонных звонков;
- уменьшение количества потерянной информации;
- сокращение времени подключения нового подрядчика;
- сокращение количества организационных ошибок;
- увеличение процента проектов, завершенных без внеплановых изменений.

Главный показатель успеха:

> Пользователь открывает Event OS не потому, что обязан, а потому что уверен — именно здесь находится актуальный контекст проекта.

---

# Product Strategy Statement

Event OS развивается не как набор функций.

Платформа развивается как единая операционная среда, в которой каждый участник мероприятия получает собственное рабочее пространство, собственный контекст и сопровождение на протяжении всего жизненного цикла события.

Любое развитие продукта должно уменьшать хаос, снижать когнитивную нагрузку и укреплять принцип единого источника истины.
